## 面向开发者的Emuera课程  
Emuera不仅是运行环境，同时对开发者来说也具有非常有用的语法检查功能。  
然而，从最近的情况来看，这个方便的功能似乎没有得到很好的利用，  
因此简单总结一下面向开发者的Emuera使用方法  

---  

### 1.不应使用默认设置  
Emuera的默认设置是面向仅玩游戏的人的，  
语法检查等功能没有发挥作用，但使用此设置不出错=没有问题的误解容易产生。  
实际上，默认设置会跳过语法检查的重要部分，被遗漏的基本语法错误不少。  
（连Lv2的警告都能轻松遗漏）  
因此，推荐开发者使用以下设置。  

- 解析标签  

勾选`加载时显示报告`  
`加载时检查参数`：`始终执行`或`更新时执行`（推荐前者，但看个人喜好）  
`最低显示警告级别`：`0`（虽然不是错误，但基本语法错误等还是没有更好）  
<u>CALLFORM系列的函数调用在最近多用的代码中不太重要，按喜好即可</u>  

- 环境标签  

`关联的文本编辑器`：平时使用的文本编辑器路径  
`命令行参数`：在编辑器中按行指定打开文件时的命令行参数（请参考所用软件的帮助等）  
<u>这样出错时点击出错行，会自动在编辑器中打开该位置</u>  

---  

### 2.解析模式选项  
Emuera有一个特殊的启动模式叫解析模式。  
这是将ERB文件或文件夹拖拽到`Emuera.exe`上启动的模式，  
使用上述开发者设置自动检查并输出结果到`Analysis.log`的模式。  
如果在变体上运行，还会考虑csv数据进行解析，所以基本的语法检查功能是足够的。  
平时使用时虽然希望启动速度快，但对于开发时想好好进行语法检查的人来说是推荐的模式。  
<u>另外，解析模式还会输出平常启动时没有的ERB文件的函数名一览</u>  

---  

### 3.最近的语法解析强化  
从1807v5开始，Emuera的语法检查功能和面向开发者的功能得到加强。  

- A.函数调用堆栈  

运行时错误中，从当前行所在的函数开始，依次显示调用来源的行，进一步显示调用来源的函数的调用来源...  
即显示函数是如何被调用的。  
在通用表达式函数中的错误等，便于排查是从哪里调用时出现问题的。  

- B.启动时变量检查中增加了数组元素越界检查  

启动时对变量参数中的常量，增加了检查其是否在元素范围内的处理。  
这样，常量情况下会报告越界的错误。  

- C.抛出错误的`THROW`  

[`THROW`](../Reference/THROW.md)指令是到达该行时强制抛出错误的指令。  
可用于调试中的特定条件确认等多种用途。  

如上所述，合理使用Emuera可以几乎消除简单语法错误残留的代码发布问题，  
无论是变体作者、口作者还是补丁作者，都希望能熟练使用。  

---  

### 4.`_fixed.config`的使用方法  
首先，如果变体方想固定某些运行环境设置，不能使用`emuera.config`。  
因为`emuera.config`是用户侧定义自身环境的，用户覆盖是预设的前提。  
（用户侧设想的是从其他变体复制粘贴等操作）  

那么，变体方想固定设置时怎么办呢？这时候CSV文件夹里的`_fixed.config`就派上用场了。  
`_fixed.config`指定的设置用户侧无法覆盖，始终优先采用`_fixed.config`的指定。  
这对绘制方法、存档数据格式等设计层面的设置非常有效。  

类似的文件还有`_default.config`，但这是在用户设置不存在时指定默认值的规格，  
现实中出场机会不多。

## Q&A  

### Q:为什么Emuera启动这么慢？  
A:Emuera启动时读取所有代码，检查`IF～ENDIF`和`CALL`等的对应关系。因此启动需要时间。  
但是，正因为如此，实际脚本处理比eramaker快。  
（虽然绘制处理是瓶颈，感觉不到）  
另外，能在启动时检查错误也是这种实现的结果。  
这里是启动速度和启动后处理速度等的权衡。  
**1.735以后的字符串读取解析处理优化大幅改善了启动时间**  

### Q:Emuera绘制太慢  
A:实际上C#并不是擅长图形绘制的语言。因此这在某种程度上是规格。   
现在如果用OpenGL或DirectX代替GDI·GDI+可能会变快，但作者没有精力做这种改动。  
有勇气的人可以试试。  

以下是一些解决方法：  
多数情况下默认设置能达到一定速度，但RadeonHD系列因PowerPlay规格GDI绘制较慢，使用GDI+的Graphics+图像缓冲设置可能更快且闪烁较少。  
（HD4XX0系列可以用CCC固定时钟，但不推荐给新手）  
另外，旧机器降低FPS设置也有效果。

## Emuera规格补充说明  
### `REPEAT～REND`（`FOR～NEXT`）的奇怪规格  
eramaker中以下代码不会循环  

``` { #language-erb title="ERB" }  
GOTO $TEST  
REPEAT 10  
	;～以下处理～  
	$TEST  
REND  
```  

那么，以下呢？  

``` { #language-erb title="ERB" }  
REPEAT 10  
	;～以下处理～  
	$TEST  
REND  
COUNT = 0  
GOTO $TEST  
```  

答案是"即使没经过`REPEAT`也会循环"。  
eramaker的规格是，  
"一旦进入循环，此后即使`GOTO`不经过`REPEAT`直接跳入内部，也会继续循环"  
这种奇怪的规格确实存在。  
Emuera当然也重现了这一点。绝不是应该使用的处理。  

---  

### 关于`CONTINUE`处理  
循环处理不可缺少的`CONTINUE`和`BREAK`两条指令  
然而，与简单明了的`BREAK`（强制跳出循环）相比，  
CONTINUE的处理常常被误解。  
这种误解在`DO～LOOP`语法中出现。  

``` { #language-erb title="ERB" }  
DO  
	;(处理)  
	CONTINUE  
LOOP 0  
```  

这段代码，因为有CONTINUE，看起来像是无限循环，但  
实际上`DO～LOOP`只会执行一次。  
这是因为`CONTINUE`的**本质是跳转到循环末尾**的规格。  
也就是说，这个循环的处理是  
<u>`CONTINUE`→`LOOP 0`的判断→判断结果为假</u>所以跳出循环  
就是这样。  

---  

### 字符串和`RETURNF`的奇怪规格  
用户定义的表达式函数通过声明标识符`#FUNCTIONS`  
可以使用`RETURNF`返回字符串。  
然而，这个`RETURNF`字符串有奇怪的机制。  
`RETURNF`返回字符串时的格式，  
与`PRINT`系列的显示或字符串赋值等不同规则。  
具体如下。  

|字符串类型|格式             |例子|  
|:-          |:-               |:-|  
|简单字符串  |"字符串"         |RETURNF "测试"|  
|字符串变量  |变量名           |RETURNF STR:0|  
|FORM字符串  |@"FORM字符串语法"|RETURNF @"%STR:1%{A:2}\@(LOCAL) ? あ # い\@"|  

最后的FORM字符串需要注意，不使用@"～"会出错。

### `PRINTCPERLINE()`的意义  
config中有`PRINTC排列数量`项，但实际上只在训练命令显示等中使用。  
也就是说，从脚本使用`PRINTC`系列时不会根据设置自动换行。  
即便如此，如果想像训练命令一样显示`USERCOM`命令等，这时就轮到这个命令登场了。  
也就是说，通过这个命令读取设置，编写相应的换行代码即可。

### `DO～LOOP`指令  

格式：  

``` { #language-erb title="ERB" }  
DO   
	;(指令)  
LOOP (条件)  
```  

补充：  
`WHILE～WEND`循环最初如果不满足`WHILE`条件，内部处理完全不执行。  
相比之下，`DO～LOOP`执行一次循环内处理后在`LOOP`行判断是否继续循环。  
如果确定至少执行一次处理，使用`DO～LOOP`会更优雅。  

---  

### `REUSELASTLINE`规格变化  
`REUSELASTLINE`在最初实现的`[私家改造]1.52q rev.2`和被正式收录的`1.60`以后规格不同。  
具体来说原本是，  

- 消除前一行，添加下一行时显示被消除的行  

变成了  

- 添加下一行时显示被消除的行  

因此，对`INPUT`，无效输入时想消除输入值的情况下，  
原本的规格下，  

``` { #language-erb title="ERB" }  
REUSELASTLINE (警告文)  
```  

就够了，但现在需要  

``` { #language-erb title="ERB" }  
CLEARLINE 1  
REUSELASTLINE (警告文)  
```  

在`@USERXXX`系列处理中仍像以前一样  
`REUSELASTLINE_` (_是半角空格)  
就能运行  
（这种情况下内部处理，所以不需要CLEARLINE）  

另外，关于这个规格差异，因改变会引发混乱，已决定不改回（通过作者间的直接对话决定）  

---  

### 位运算系列指令  
虽然方便，但位运算是出了名的复杂。  
Emuera实现了`1pN`这样的二进制表示，并增加了许多位运算用运算符，使位运算更容易。  
不过，对于有编程经验的人还好，否则即使这样实现也很痛苦。  
因此，准备了`GETBIT`、`SETBIT`、`CLEARBIT`、`INVERTBIT`。  
参考：[参考/BIT操作系列](../Reference/BIT_OPERATION.md)  

格式：  

``` { #language-erb title="ERB" }  
GETBIT (操作变量)、(位位置)  
;获取目标变量的2^(位位置)位  
;（GETBIT可以作为语句内函数使用）  

SETBIT (操作变量)、(位位置)  
;将目标变量的2^(位位置)位设为1  

CLEARBIT (操作变量)、(位位置)  
;将目标变量的2^(位位置)位设为0  

INVERTBIT (操作变量)、(位位置)  
;反转目标变量的2^(位位置)位（0→1，1→0）  
```  

这种方法的优点是，  

- 不需要计算目标位的值。  
- 位位置指定与1pN不同，可以使用变量，便于统一处理。  

缺点是  

- 对懂的人来说过于繁琐。  
- 用运算符等看起来更酷。  

---  

### Shift-JIS和Unicode字符串处理差异  
Emuera中基本准备了3个字符串长度获取指令。  

``` { #language-erb title="ERB" }  
STRLEN (字符串)  
STRLENS (字符串表达式)  
STRLENFORM (FORM语法)  
```  

这些都获取Shift-JIS的字符串长度。  
与此相对，  

``` { #language-erb title="ERB" }  
STRLENU (字符串)  
STRLENSU (字符串表达式)  
STRLENFORMU (FORM语法)  
```  

以Unicode获取字符串长度。  
最大的差异是Shift-JIS将汉字1个字符计为2个字符，而Unicode将汉字也计为1个字符。  

---  

### LOCAL变量也应避免的事情  
`LOCAL`是非常好用的变量，但根据ERB规格仍有应避免的现象。  

- 跨相同事件函数使用  

事件函数根据ERB规格可以定义多个。  
这意味着`LOCAL`在所有函数中共用，  
跨相同事件函数使用`LOCAL`的处理极有可能因其他同名函数介入而崩溃  
建议这种情况下使用`TFLAG`等  

- 使用`LOCAL@～`  

`LOCAL`变量可以从函数外通过`LOCAL@`引用  
但这是"为了调试"的措施，  
仅用于确认值没有特别问题，但如果开始赋值，  
可能成为bug原因，也使调试困难  
完全不推荐在通常代码中使用  
（未来希望将`LOCAL@～`设为只读）  
建议考虑不需要这样实现的设计  

- 作为static变量使用  
`LOCAL`在函数结束后值也保持，  
即行为类似C语言的static（静态）变量  
但即便如此，也不应将`LOCAL`作为static变量使用  
考虑以下代码就能明白  

``` { #language-erb title="ERB" }  
@TEST  
IF LOCAL == 0  
	;～  
ELSEIF LOCAL == 1  
	;～  
ELSE  
	;～  
ENDIF  
LOCAL = （某种条件下决定）  
```  

这段代码根据最后设置的`LOCAL`值决定下次行为  
看起来`LOCAL`是static，似乎没问题  
但这段代码在存档加载后可能崩溃  
`LOCAL`是不保存在存档数据中的变量，  

- 返回标题  
- 加载存档数据  

等会清除值  
也就是说，依赖前次设置值的处理很容易成为bug原因  
`LOCAL`应仅用于一次处理的封闭使用  

---  

### 应该用`IF`还是`SELECTCASE`  
`IF`和`SELECTCASE`在`A = RAND:5`后用`A`分支的情况下  
都可以写类似代码，  
但处理速度差异很大，  
`IF`需要约`SELECTCASE`两倍的处理时间  
上述简单值分支情况下，  
可以说`SELECTCASE`比`IF`更有效率  

另外，口上中做同样事情时，使用`PRINTDATA`系列  
可能代码更短，处理更快  

---  

### `CALLF`和伪设置器  
`CALLF`指令是  

```  
调用表达式函数，忽略返回值  
```  

看似没什么用的指令。  
但有如下用法  

``` { #language-erb title="ERB" }  
@SET_VALUE(ARG, ARG:1)  
#FUNCTION  
RETURNF VALUE("SET", ARG, ARG:1)  

@GET_VALUE(ARG)  
#FUNCTION  
RETURNF VALUE("GET", ARG)  

@VALUE(ARGS, ARG, ARG:1)  
#FUNCTION  
IF ARGS == "GET"  
	RETURNF LOCAL:ARG  
ELSEIF ARGS == "SET"  
	LOCAL:ARG = ARG:1  
ENDIF  
```  

这样，函数`@VALUE`的`LOCAL`就可以不使用`LOCAL@`引用。  
不使用单字符变量，在多个函数间引用数组时有用。

## 各种复杂细节  
### 私家改造中的脚本处理加速内幕  
最近的私家改造中，为了加速脚本处理，  
其实现非常巧妙。  

迄今为止的脚本处理简单来说是这样的  

```  
(主程序)→（脚本执行开始）→（处理准备）  
→（脚本实际处理）→（无限循环判定程序）  
→(主程序)  
```  

这就是每一行都重复的现有代码。  
可以看出，这是效率很低的处理。  
现在的私家改造中重构如下。  

```  
(主程序)→（脚本执行开始）  
→｛（处理准备）→（脚本处理）→（无限循环判定）｝×n  
→（主程序)  
```  

重点是第2行。这个处理中只要不需要返回主程序，  
就不断循环执行脚本，成功减少了函数调用次数。  
另外，对一些高频使用的处理特别处理路径，  
成功减少了处理时间，实现了`REPEAT～REND`等的加速。

### Emuera错误检查内容  
Emuera启动后读取代码，如有错误则显示。  
显示有两种模式，  

- 文件加载时显示的错误  
	- `*****.ERB加载中…`下显示的错误  
- 文件加载后语法检查显示的错误  
	- 文件加载结束后，显示标题前显示的错误  

这是根据代码检查时间尺度区分的。  
具体按以下顺序检查错误。  

- 文件加载时错误检查  
	- 1 可解析行的确认中的错误检查  
		- a.`[SKIPSTART]`或`#`开头的行  
			- 确认正确使用，错误则显示错误  
  	- b.函数声明行  
			- 确认声明格式正确，错误则显示错误  
		- c.`+` or `-`开头的行  
			- 确认是前置增量·减量，否则显示错误  
		- d.以指令·变量开头的行  
			- 首先，确认开头字符串是指令或变量  
			- 如果都不是则显示错误  
			- 如果开头字符串不正确（包含不该有的符号如`\`或`$`等）则抛出异常，停止读取（1731t以后改为不停止）  
		- e.预计是变量赋值行时  
			- 检查是否是赋值格式，如果不是则显示错误  
	- 2 文件加载后语法检查中的错误检查  
		- a.声明函数内容检查  
			- `#FUNCTION`声明的函数，检查有没有不能用的指令  
			- 「启动时解析参数」时检查参数格式是否正确  
			- `IF～ELSEIF～ELSE～ENDIF`或`REPEAT～REND`等成对使用的指令对应关系检查  
			- `CALL`等目标检查（`CALLFORM`等运行时决定目标的指令不检查）

### `PRINT`系列和`PRINTFORM`系列处理量差异  
显示不包含变量的平文时，`PRINT`系列和`PRINTFORM`系列哪个内部处理量更少。  
答案是（不用说也知道）`PRINT`系列。  
`PRINT`系列将参数直接显示，处理量很少。  

- PRINT系列  
参数检查：参数直接作为字符串赋值  
指令执行内容：取出参数，直接传给显示函数  

- PRINTFORM系列  
参数检查：取出参数，检查变量存在等，保存为对应string.Format格式的字符串  
指令执行内容：取出参数，将变量内容填入格式，生成显示字符串传给显示函数  

这样`PRINT`系列和`PRINTFORM`系列即使平文处理量也有天壤之别。  
顺便1755a中`PRINTFORM`系列给平文时的处理速度大幅提升，差距应该缩小了（但显然还是慢）

### IF语句条件判断顺序  
考虑以下IF语句  
``` { #language-erb title="ERB" }  
IF A && (B || (C && D))  
```  
在这个语法中，条件A～D按什么顺序判断？  
（为简化，不考虑短路评估）  
单纯考虑()优先，应该是C→D→B→A，但实际Emuera处理是A→B→C→D顺序。  

为什么会这样，是因为Emuera语法处理方法。  
上述语法Emuera解释如下。  
```  
1, Y = C && D，然后  
	IF A && (B || Y)  
1. X = B || Y，然后  
	IF A && X  
```  

实际处理如下。  

```  
1. 评估A && X  
	1a. 评估左A  
	1b. 评估右X→X = B || Y所以评估B || Y  
1. 评估B || Y  
	2a. 评估左B  
	2b. 评估右Y→Y = C && D所以评估C && D  
1. 评估C && D  
	3a. 评估左C  
	3b. 评估右D  
```  

因此判断顺序是A→B→C→D。  
想想就知道，判断结果是正确的，所以这种方法没有问题，短路判断优先左，反而这样更合理。  
（因为如果左为假就不需要看右的()内，处理减少，左为真时处理也与先评估右()内时相同，综合看处理量减少。  
从这个意义上说，如果仅考虑Emuera，只要不出错，把最难成立的条件放在最前也不是毫无意义的编码。  
当然现实来说，如Q&A所说，Emuera处理的瓶颈是绘制处理，纠结这里不会显著提升处理速度。）

### 为什么`VARSET`快  
用指定值初始化变量数组整体的VARSET指令有类似实现  

``` { #language-erb title="ERB" }  
REPEAT N(数组大小)  
	A:N = 0  
REND  
```  

相比处理速度至少快一万倍。  
（`VARSET`即使数组元素数一百万个也能瞬间处理）  
这是有原因的。  

`VARSET`调用时，内部调用给定数组，执行赋值循环处理。  
这个内部循环处理在运行时优化，执行非常快。  
另一方面，`REPEAT～REND`情况下执行以下处理。  

```  
1. 进入REPEAT  
	（如果是首次设置COUNT为0，  
	从REND跳转来则COUNT加1并结束判断）  
2. 执行A:COUNT = 0  
3. REND行什么都不做回到REPEAT行  
```  

（1～3重复设定次数）  
这样`REPEAT～REND`不仅有变量赋值处理，还要处理3行代码驱动。  
结果不仅处理量增加，处理复杂化也使运行时优化困难，非常耗时。  
一般地说，用内部指令实现与ERB脚本相同处理，内部指令通常快得多。  
（特别是对数组循环的情况）  
不过，由于有意义差异的长重代码本身不多，体验这种差异的情况并不多。

### 代码重读规格和内存消耗增加  
现在的Emuera有ERB文件重读功能，但每次使用都会增加内存消耗。  
这是不可避免的。  
Emuera的ERB代码处理，启动时逐行读取所有代码，装入类中管理，这时保持下一行信息。  

ERB重读不仅在系统输入等待，`INPUT`等输入等待指令中也能进行，  
这时当前`INPUT`所在的函数文件重读，代码信息替换会怎样？  
答案很简单。  

**Emuera会丢失要执行的代码并出错。**  

因此，重读时不能丢弃现有代码。  

**所以，与已读取代码分开，新代码栈机制。**  

通过定义函数信息使新代码执行。  
这个规格下，运行中的函数会终止，再次调用前按旧代码运行，这是无法避免的。  
另外，重读后的旧代码，重读后文件代码添加后新旧难区分，所以不删除保留。因此，每次重读代码栈增加，内存消耗也增加。  
所以，除了开发中等必要情况，这还是安全功能。
