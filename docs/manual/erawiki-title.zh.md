## 准备制作标题画面  
虽然还没有掌握原版系统的机制，但初始环境已经准备好了。  

想要快点开始制作游戏。  
那就来制作表达这种心意的标题画面吧。  

回想一下现有的变体作品，  
有些是像有统一规范一样的熟悉而简单的黑色画面，  
有些是ASCII艺术，或使用了图片，各种各样的标题画面。  

开头说的内容似乎有些矛盾，  
实际上era的标题画面并不一定要做。  

所以，这一项会暂时成为标题欺诈。  
但是，最终即使需要自己动手制作也会有所帮助，希望您能读下去。  

---  

### GameBase.csv  

打开CSV文件夹中的`GameBase.csv`。  

```  
代码,326136  
版本,110  
标题,erakanon(minimum)  
作者,佐藤敏（社团貘）  
制作年份,2005-2006  
附加信息,（※这是调教SLG制作工具eramaker的示例游戏。）  
```  

上面这样写着。  

---  

### 更改标题  

将  

```  
タイトル,erakanon(minimum)  
```  

改为  

```  
タイトル,你想到的标题  
```  

然后保存，启动Emuera.exe看看。  

窗口左上角显示的名称变成了  

>你的标题 0.11  

画面中央变成了  

>你的标题  

也许你已经注意到了，只要修改`Gamebase.csv`，  
显示的信息就会改变，标题画面就完成了。  

我想应该有人会想：「不对！我想象中的是更酷的标题！我想自己制作！！」  
也有人会有这样的想法。  

但是，即使想自己制作标题画面，也要尝试使用在`Gamebase.csv`中输入的信息。  

当你改变主意想更改标题时，  
或者继续开发想更改游戏版本时，  
必须更改的地方越少越好。  

即使要自己制作，如果建立『只需修改Gamebase.csv，就能自动更改标题画面显示信息』的机制，  
以后的变更点就能集中到一处，变得更加方便。  

仅此而已的话，  
可能会觉得『不用Gamebase.csv，只管理标题显示用的文件，不是一样可以将变更点集中到一个地方吗？』  

但是，`Gamebase.csv`变量是不可赋值的（WINDOW_TITLE可以赋值），  
而且通过指定`Gamebase.csv`，还能够管理版本相关的存档数据加载许可等，  
有很多方便的功能。还有个优点是别人看的时候容易知道信息在哪里。  

有时也有人会在确认`Gamebase.csv`并检查版本后向我们报告错误。  

所以，不管实际是否使用，了解一下它有什么用途总是好的。  

---  

### 更改窗口标题  

在  

```  
タイトル,你想到的标题  
```  

下一行左右，添加如下内容：  

```  
ウィンドウタイトル,你想到的窗口标题  
```  

试试看。  

画面中央仍为  

>『你的标题』  

而窗口左上角显示的名称从  

>『你的标题 0.11』  

变为  

>『你的窗口标题』  

eramaker说明书中没有记载这一点。  
因为这是Emuera新增的功能。  

- [EmueraWiki→变量→csv相关→WINDOW_TITLE](https://evilmask.gitlab.io/emuera.em.doc/Emuera/variables.html#window_title)  

```  
初始值设定为gamebase.csv中的"窗口标题"的值。  
如果没有设定"窗口标题"，  
则根据"标题"和"版本"生成。  
如果也没有设定"标题"，则为"Emuera"。  
```  

上面这样写着。  

如果不想在标题中显示版本等，  
想改变显示内容时，指定窗口标题会比较好。

### 更改作者  

将  

```  
作者,佐藤敏（サークル獏）  
```  

改为  

```  
作者,你的笔名  
```  

试试看。  

这个变体的作者就是你。  
既然项目中有用于假定更改作者名的项目，  
那么更改这里的作者项目应该没有问题。  

关于era原版和Emuera制作者的版权，请另行附带README文件供阅读。  
（Emuera设想了附带README文件的情况。  
　eramaker似乎没有独立的许可证声明README文件。  
　在标题介绍中保留、在自制的README侧贴出网站介绍、  
　通过附带说明文字进行某种引导等方式都可以）  

尊敬前辈并尊重版权是很重要的。  
但如果过于拘谨保持原作者不变，会出现另一个问题。  
可能会让工具制作者或基础变体制作者被认为参与了自己的作品制作，  
或是由于修改引起的错误询问会被发送到原作者那里，造成困扰。  

所以让我们明确说明联系处吧。  
在此基础上，也可以写上免责声明，说明无法回应咨询。

### 什么是代码？  
试着修改其他项目吧。  

最让人摸不着头脑的应该是  

>代码,326136  

这行吧。  

即使不明白意思也没关系，想快点推进的话先写出结论，  
暂时放一个100000～100000000左右不容易重复的数字就可以了。  

- [Cbaku2 eramaker CSV文件格式（暂定版）](https://cbaku2.sakura.ne.jp/b/erakanon/eramacsv.html)  

上面写着：  

>代码,(数值)  
>将游戏代码设为(数值)。  
>这是为了防止误加载其他游戏的存档数据而使用的。  
>(数值)可以是任意值。  

也就是说，只要和其他游戏不重复就行，看起来像ID一样的东西。  

有些人可能希望指定尽可能多的位数，以尽量避免重复数字。  
位数的极限是多少呢？  

- [EmueraWiki→与eramaker的不同点→gamebase.csv『代码』的读取方法](https://evilmask.gitlab.io/emuera.em.doc/Emuera/differences_of_Emuera_and_eramaker.html#gamebasecsv)  

根据这里写的说明，  
eramaker的情况下，超过位数限制时会部分截取自动指定。  

Emuera的情况下，超过位数限制时会按0处理。  

说0的话，无论游戏代码如何都会去加载，上面写着。  

范围是『`-9223372036854775808～9223372036854775807`』（64位）。  

为了防止误操作，应避开相同的数字串、容易重复的整数编号等。

### 什么是版本？  
一直覆盖保存的话失败时无法恢复。  

最好在一个阶段完成后进行保存，并以此为基础添加新元素。  

这样如果失败了，也比较容易返回到已保存的数据。  

为了不让备份变得混乱，  
根据制作进度附上的编号就是版本号。  

更新时逐次提升数字，以便清楚地看出更新到哪里了。  

- [eramaker CSV文件格式（暂定版）](https://cbaku2.sakura.ne.jp/b/erakanon/eramacsv.html)  

上面写着：  

>在画面上，显示的是(数值)除以1000的结果（如100显示为0.10）  

当前版本是：  

```  
バージョン,110  
```  

改成  

```  
バージョン,100  
```  

试试看。  

标题画面显示的数字变成0.10。  

改成  

```  
バージョン,112  
```  

试试看。  

标题画面显示的数字变成0.112。  

默认情况下，小数点后两位会被显示，  
如果没有指定第三位小数，则会被省略。  

先将这些记在心里的一角，  
实际如何管理因人而异，  
请按自己便于管理的方式进行指定。  

举个例子：  

- 第一位是主版本号  
（进行对整体有影响的重大更新，或失去存档兼容性时）  

- 小数点后第一至二位是次版本号  
（进行功能等细小追加时）  

- 小数点后第三位是错误修复  

等等的区分方式（可能是默认设定所预想的区分方式）  

第一位是主版本号  
小数点后是次版本号  
等等的区分方式  

第一位是主版本号  
小数点后第一位是次版本号  
小数点后第二位是补丁  
小数点后第三位是错误修复  
等等的区分方式  

或者不使用自动分割显示，增加位数到一万，  
以`X.XX.XX`的形式显示，表示兼容性丧失.功能追加.错误修复  
等等的区分方式都有。  

无论如何，补丁作者通常不会修改`Gamebase.csv`，  
因此如果没有人为之整理，这些信息可能完全不被提及。  

也有版本管理系统，使用的人很多。  

- [era系列讨论汇总Wiki V3→系统改造Q&A→其他→使用版本管理系统](https://evilmask.gitlab.io/emuera.em.doc/manual/erawiki-modification-QandA.html#_17)

### 接受不同版本？  
一开始设置为最小版本。如果是1则设为1。  

进行失去兼容性的更新时，仅作"无兼容性"的通知的话，  
没注意到的玩家可能会继续使用旧存档，导致报错。  

进行失去兼容性的更新时，如果设置了此项，  
比该版本旧的存档数据将无法加载。  

一般情况下，进行部分变量替换等更新时，  
通常会在加载后立即执行的『`@EVENTLOAD`』内部编写处理来弥补差异，  
以维持兼容性。  

<!--//(2021/05/12 wiki编辑帖子中建议添加，感谢） -->  

放弃兼容性通常是大规模更新时才采取的措施，  
否则很少采用。游玩人数越多，  
"如果能不废弃重要存档数据的话，就不必升级版本！"   
感到震惊的人也会更多。短篇游戏可能不在这个范围内。  

即使放弃兼容性可能导致错误发生，比起让存档无法使用，  
某些情况下还是选择接受错误。
