本页面主要汇总了面向**新变体**或**大型补丁作者**的编程信息。  
除非另有说明，否则默认前提是能在当时**最新版本的 Emuera**上运行。  
在 eramaker 或旧版 Emuera 中可能无法正常工作。  

## 基础知识  
### 关于私有变量（不要只用 A～Z 或 LOCAL，请使用 #DIM） { #azlocaldim }
- 仅在函数内部使用的变量，请声明为 `#DIM` 后使用。  
- 想要增加保存数据时，请在 ERH 文件中编写 `#DIM` 来使用。  
- 虽然想不出平时必须使用 `LOCAL` 的理由，但在示例代码中可能会用到。  

在旧的 erabasic 中，临时使用的变量通常使用单字母变量 `A～Z`，但现在已不推荐这样做。  
因为这些变量在任何地方都可以使用，如果在 `CALL` 调用的子函数中被改写，可能会导致在不知不觉中数值发生变化。  
但是，除了记录循环次数或保存计算中间过程外，过去没有其他可用的变量。  

因此，作为只能在某个函数中使用的变量（局部变量），追加了 `LOCAL` 变量。（字符串型的局部变量是 `LOCALS`）  
然而，因为它们的名字全都是 `LOCAL`，如果用一两个还好，一旦使用了 `LOCAL:1`、`LOCAL:4` 等多个，不仅程序外观变差，也难以分辨每个变量具体是用来做什么的。  

于是，进一步新增的功能就是**私有变量**。通过编写 `#DIM` 加上想要的变量名，就可以创建仅在该函数中可用的新变量。  

``` { #language-erb title="ERB" }  
@EVENTFIRST  
#DIM LCOUNT  
LCOUNT = 99  
```  

`#DIM` 必须写在每个 `@～～～`（函数标签）的紧后方，否则无效。它不能在其他函数中使用，也不会被保存。  
字符串型可以用 `#DIMS` 创建。也可以创建巨大的数组等。详情请参阅以下页面：  
[用户定义的变量](../Emuera/user_defined_variables.zh.md)  

`LOCAL` 还有另一种用法，即像 `LOCAL@USER_SHOP` 这样在后面加上函数名，就可以从其他函数改写该变量。（这原本是用于调试的功能）  
以前曾利用这一点来弥补全局变量的不足，但如果这样使用，它就既不是局部也不是全局，最终会出现和 `A～Z` 一样的问题。  
现在这种情况下也是通过 `#DIM` 创建新名字的变量，但不是写在 `@～～～` 的紧后方，而是创建 **ERH 文件** 并在其中编写。  
可以决定是否保存，或者是否保存到全局数据中。  
最近的大型变体大多使用 ERH，所以如果遇到不熟悉名字的变量感到困扰时，请寻找扩展名为 `.ERH` 的文件。  
（通常放在 ERB 文件夹的根目录下，也可能有多个）  
[关于 ERH (头文件)](../Emuera/ERH.zh.md)  

现在还要刻意使用 `LOCAL` 的理由，大概只有在制作补丁时不想大幅修改程序，或者不想升级 Emuera 版本的时候吧。  
不过，本页面内用于解说的示例代码中可能会使用 `LOCAL`。  
这是因为当示例只是函数的一部分而非整体时，与必须限定写在函数标签紧后方的 `#DIM` 兼容性不好。  
在实际制作变体或补丁时，请将 `LOCAL` 或 `LOCAL:1` 等部分替换为用 `#DIM` 创建的变量。  

最后说明一下与一般编程语言中局部变量的区别。（没用过 erabasic 以外语言的人可以忽略）  
Emuera 的局部变量，与 C 语言、JavaScript、Ruby 等当今流行的编程语言中的局部变量**不同**。`LOCAL` 相当于全局变量。  
即使是 `#DIM` 声明，上次函数调用时的数据也会保留，性质上接近全局变量。  
通常这不会造成困扰，但在制作所谓的**递归处理**等时会成为问题。同时被调用的函数都会读写同一个变量。  
要在 Emuera 中制作一般意义上的局部变量，请在声明 `#DIM` 时加上 `DYNAMIC` 关键字。

### 函数中的移动方法（控制结构） { #_2 }

erabasic 的程序（其他编程语言也大致如此）基本是按照从上到下的书写顺序执行的。这称为**顺序执行**。  
如果是像小说或电影那样按顺序推进的东西还好，但游戏会根据条件改变接下来的行动。这种用于改变顺序的程序称为**控制结构**。  

就像游戏书一样，写着“如果有勇者之剑则前往第 23 页”，读者会根据指示翻开指定的页面，而不是下一页。这就是面向读者的控制结构。  

控制结构包括像 `CALL` 或 `JUMP` 这样使用其他函数的命令，也包括游戏结束命令等，但这里主要讲述在**函数内部**改变执行顺序的方法。  

| 语句名称 | 向前移动 | 向后移动 | 移入其他控制结构内部 |  
| :--- | :--- | :--- | :--- |  
| [TRYGOTO・GOTOFORM](../Reference/GOTO.zh.md) | $标签 | $标签 | 可以但不推荐 |  
| [GOTO](../Reference/GOTO.zh.md) | $标签 | $标签 | 可以但不推荐 |  
| [LOOP](../Reference/DO.zh.md)・[WHILE](../Reference/WHILE.zh.md)・[FOR](../Reference/FOR.zh.md) | 循环开头 | 循环结尾 | ❌ |  
| [IF](../Reference/IF.zh.md)・[SELECTCASE](../Reference/SELECTCASE.zh.md) | ELSE・ENDIF・CASE | ❌ | ❌ |  
| [RESTART](../Reference/RESTART.zh.md) | ❌ | 函数开头 | ❌ |  

基本上，与其使用各种功能强大的结构，不如使用范围限定的命令，这样程序更安全且易读。  
如果觉得哪个都可以用，请优先使用上表中**靠下**的项。  

控制结构的基础是 `GOTO` 语句。只要给它加上 `IF` 语句或简单的计算式，其他所有结构都可以用 `GOTO` 重写。  
但因为过于强大，容易发生意想不到的事情，所以建议**尽量不使用**。  
（想知道详情的人请搜索“结构化编程”）  

必须需要对应的标签也是一个缺点，与其他写法相比，难以看出哪个标签与哪个 `GOTO` 对应，导致结构不清晰。  
在旧的 erabasic 中，为了在输入结果不正确时进行循环，频繁使用 `GOTO` (`$INPUT_LOOP`)，但大部分可以用 `LOOP` 语句或 `WHILE` 语句替换。EM+EE 中还有 `BINPUT` 命令。  

只有 `GOTO` 能做到的是移入其他控制结构内部，但这最好**尽量避免**。  
例如，从 `FOR` 循环外部 `GOTO` 进循环内部，就会搞不清楚现在是第几次循环。  
如果是 `IF` 语句，可能会出现条件不满足却执行的情况。虽然不是 bug，Emuera 会按规则正确动作，但该规则未必与你所想的一致。  
在同一控制结构内的移动，或从结构内向外的移动是没有问题的。特别是从多重嵌套的循环中一口气跳出，是 `GOTO` 的有效用法之一。  
（如果不使用 `GOTO`，就需要组合多个 `BREAK`、`CONTINUE`、`IF` 语句等，反而变得难以理解）  

`TRY` 系控制结构用于补丁或口上等，即使该函数（或其所在的文件）不存在也能运行的机制中。  
`FORM` 系控制结构用于根据变量状态改变跳转目的地，而不想写大量的 `SELECTCASE` 和 `GOTO`，或者以后需要增加数量时。  
缺点是启动时无法判断标签是否正确，只有执行后才知道，因此难以发现 bug。  
除了 `CALL` 和 `JUMP`，`GOTO` 仅限于该函数内部，所以我想没什么特别有效的场景。  

- **重复 (`LOOP`, `WHILE`, `FOR`)**  
重复也是控制结构的一种。  
按指定条件重复本质上是带条件的 `GOTO`，但除此之外，还可以用 `CONTINUE` 实现向开头部分的 `GOTO`，用 `BREAK` 实现向该控制结构紧随其后的 `GOTO`。  
如果在（无限）循环的最后写上 `BREAK`，就不会变成重复；如果不执行 `CONTINUE` 就直接继续向下，就可以替换向后的 `GOTO` 语句。  

- **分支 (`IF`, `SELECTCASE`)**  
条件不匹配的 `IF` 语句，等同于向 `ELSE` 紧随其后（若无 `ELSE` 则向 `ENDIF` 紧随其后）的 `GOTO`。`SELECTCASE` 是可以一次性设置多个条件的 `GOTO`。  
分支可以用于向前推进的控制，但**不能**用于向后返回。如果想有条件地向后返回，需要与其他命令组合使用。  

- **RESTART**  
等同于向函数开头部分的 `GOTO`。用于 `@SHOP` 或 `@ABLUP` 等取消操作时，回到最初画面重做的情况。  
并不是从头开始（变量不会初始化），而是向开头跳转，所以变量保持变更后的状态。  
如果不想去最开头，而是想去开头稍下方的位置，可以在该处设置标签并使用 `GOTO`，或者使用重复结构与 `CONTINUE`。

### 重复处理的写法 (`FOR` 与 `REPEAT` 的区别及推荐写法) { #forrepeat }
- 尽量不使用 `REPEAT`  
- `FOR` 应与私有变量或局部变量配合使用  
- `WHILE` 和 `DO` 面向高级用户。用于难以预先把握循环次数等情况  

在 erabasic 中，频繁出现“将同样的事情重复多次”的处理。  
最易懂的例子是持有角色的一览表。显示第 1 个角色的名字和参数，显示第 2 个角色的名字和参数……如此重复制作。  
全员体力恢复时也一样，增加第 1 个人的 HP，并对人数重复此操作。  

`REPEAT～REND` 是 erabasic 初期就开始使用的重复处理结构。  
虽然写起来简单，但已知存在几个问题。  
用于查询次数的 `COUNT` 变量是全局变量，因此无法构建两个 `REPEAT` 重叠的机制；如果在 `REPEAT` 中 `CALL` 的函数里使用 `REPEAT`，`CALL` 结束后顺序会变得乱七八糟。  

为此准备了 [FOR～NEXT](../Reference/FOR.zh.md) 结构。  
因为可以使用 `COUNT` 以外的变量，所以不会发生上述问题。  
（也可以使用包括 `COUNT` 在内的全局变量，但那和 `REPEAT` 一样，所以通常使用私有变量）  
数字也可以不从 0 开始，例如想排除“你（0 号角色）”时，可以从编号 1 开始循环。  
其他编程语言可以在 `FOR` 语句内部声明专用的局部变量，但 Emuera 的 `FOR` 语句没有此功能，请像其他变量一样用 `#DIM` 声明。  

`FOR` 使用的变量名随意，但决定好“重复使用时就用这个名字”，日后查看时会更容易理解。  
其他语言习惯上用 `i`，多重循环时用 `i, j, k` 等，但 erabasic 中 `A～Z` 是全局变量，且不区分大小写，所以不能用这种方法。  
方案有很多：为了让人明白是局部变量而在开头加 `L` 变成 `LCOUNT`，缩写 `COUNT` 为 `CNT`，为了与全局变量区分而加 `_` 变成 `_I`，甚至直接用日语 `カウンタ` (计数器) 等等。请选择长度和易读性符合你喜好的方式。  

``` { #language-erb title="ERB" }  
;例：全员体力设为 MAX  
@～～～～  
#DIM LCOUNT  

FOR LCOUNT, 0, CHARANUM  
    BASE:LCOUNT:体力 = MAXBASE:LCOUNT:体力  
NEXT  
```  

另外可用作重复的结构还有 [WHILE～WEND](../Reference/WHILE.zh.md)。  
主要用于不知道要循环多少次的情况，两者非常相似，区别在于是在循环前检查结束条件，还是在循环后检查。  
简单来说，有可能一次都不执行循环内内容时用 `WHILE`，至少要执行一次时用 `LOOP` (`DO`)。  
不过根据 `BREAK` 和 `IF` 的写法，两者都能实现相同的效果，只要能正确运行，剩下的就是喜好问题。  
两者都不设置计数器变量，如果想知道是第几次循环，需要自己在循环前将局部变量设为 0，并在每次循环时加 1。  
常用的模式是无限循环直到 `BREAK`，`WHILE 1～WEND` 和 `DO～LOOP 1` 动作相同。  
（条件部分只有 `1` 时必然满足条件。数字是 2、3 或 999 都可以，只要不是 0，但习惯上使用 1）  

如果没有使用过其他语言，可能很难想象 `WHILE` 和 `DO` 该在什么时候使用。  
调查实际变体中的用例，发现有：独特的排序处理（Sort）、持续减少其他珠子直到否定之珠消失、重复直到升级时的参数分配完成……等用法。  
虽然用大得离谱的数字的 `FOR` 语句，或者 `IF` 与 `GOTO` 的组合也能实现，但写下无意义的大数字让人心里不舒服，用 `GOTO` 又要思考标签名很麻烦，所以用 `WHILE` 或 `DO` 写起来更清爽。  

例如在别的项目中显示 CSV 的角色列表时，考虑到中途编号可能有缺号而使用了 `FOR` 语句，但如果确定没有缺号，就可以使用 `WHILE` (`DO`)。  
制作无限循环，在 `EXISTCSV` 失败时 `BREAK` 即可，非常智能。  

**使用例：** “是/否”选择题，直到回答“是”才继续的程序  

``` { #language-erb title="ERB" }  
PRINTL 我相信你会选“是”……会选吧？  
DO  
    PRINTL [0] 是  
    PRINTL [1] 否  
    INPUT  
    IF RESULT==0  
        BREAK  
    ENDIF  
    PRINTL 再说一遍。你要选的是“是”  
LOOP 1  
```

### RESULT 与表达式函数 { #result }
`RESULT` 是用于返回函数结果的变量。  
`RESULT` 最常用的地方大概是 `INPUT` 命令之后，但无论 `CALL` 哪个函数，`RESULT` 都会被改写。  
如果要执行多个函数并将其结果相加，如果不每次都把 `RESULT` 的内容复制到私有变量中，就只会知道最后一个执行函数的 `RESULT`。  

既然反正要放入私有变量，使用**表达式函数**会更快。内置函数大多也准备了表达式函数版本。  

``` { #language-erb title="ERB" }  
;普通函数调用的情况  
CALL TEST 70  
LOCAL = RESULT  

;表达式函数的情况  
LOCAL = TEST(70)  
```  

[自己创建的函数也可以做成表达式函数。](../Emuera/user_defined_in_expression_function.zh.md)  
符合以下情况的，做成表达式函数通常会更方便：  
- 不进行文字输入（如 `INPUT` 等）  
- 不通过 `PRINT` 等语句显示文字  
- 不改写 `CFLAG` 或 `ABL` 等变量（仅读取是安全的）

### `IF`・`ELSEIF` 的集合或许可以换成 `SELECTCASE` 语句 { #ifelseifselectcase }
有时需要根据一个变量、计算结果或乱数等进行大量分支。  
比如根据输入得出不同结果，或根据乱数得出不同结果。  
这种情况下，如果用 `IF` 语句，必须在每个 `IF` 或 `ELSEIF` 后面逐个编写评估式。  
这相当麻烦，也是导致错误混入的原因。  
此时派上用场的是 [SELECTCASE 语句](../Reference/SELECTCASE.zh.md)。  
这是一个评估一个对象并进行多重分支的命令，比 `IF` 更快。  
只需要在 `SELECTCASE` 后面写一次评估对象。  
之后只需在 `CASE` 后面写条件即可。变得相当清爽。  
如果是以上/以下可用 `IS`，询问范围可用 `TO` 等，详情请点击上方链接。  
结尾是 `ENDSELECT`。很简单吧。  

``` { #language-erb title="ERB" }  
;试着做了一个比单纯用 LOCAL 分支稍微麻烦点的例子  
;使用 IF 的分支  
IF LOCAL+LOCAL:1 == 0  
    PRINT 是 0  
ELSEIF LOCAL+LOCAL:1 == 1  
    PRINT 是 1  
ELSEIF LOCAL+LOCAL:1 == 2  
    PRINT 是 2  
ELSEIF LOCAL+LOCAL:1 == 3  
    PRINT 是 3  
ELSE  
    PRINT 不是 0 到 3  
ENDIF  

;使用 SELECTCASE 的分支  
SELECTCASE LOCAL+LOCAL:1  
    CASE 0  
        PRINT 是 0  
    CASE 1  
        PRINT 是 1  
    CASE 2  
        PRINT 是 2  
    CASE 3  
        PRINT 是 3  
    CASEELSE  
        PRINT 不是 0 到 3  
ENDSELECT  
```

### 关于初始设定  
有 CSV 和 ERB 两种设定方法，但一旦设定后不再更改的东西、仅在标题画面使用的东西等，只能用 CSV 设定。  
除了下表之外还有一些，但大体上可以在 [GAMEBASE.CSV](../eramaker/CSV_format.zh.md) 或 [_replace.csv](../Emuera/replace.zh.md) 中设定，这里没写的就是用 ERB 设定的东西。  

| 项目 | 用于设定的 CSV |  
| :--- | :--- |  
| 标题・作者名・制作年份等 | GAMEBASE.CSV (※1) |  
| 初始状态下存在的角色 | GAMEBASE.CSV (※1※2) |  
| 角色名、初始能力 | CHARA*.CSV |  
| Now Loading 显示 | _replace.csv |  
| 金钱单位 | _replace.csv |  
| 污垢的初始值 | _replace.csv |  
| TINPUT 的时间结束显示 | _replace.csv |  
| EXPLV 上升的时机 | _replace.csv |  
| PALAMLV 上升的时机 | _replace.csv |  
| RELATION 未指定时的值 | _replace.csv |  

※1 如果定义了 `@SYSTEM_TITLE` 则无效  
※2 0 号角色强制加入，除 0 号外只能指定 1 名。  

所持金和初始物品通常在 `@EVENT_FIRST` 函数中设定。因为只在开始新游戏时执行一次，适合做初始设定。  
也常采用在设定前插入难度选择，根据难度改变设定的流程。  

角色也一样。0 号角色（大多数变体中是“你”）会自动加入，但如果需要其他初始加入的角色，必须手动添加。  
如果只有 1 人可以用 `GAMEBASE.CSV`，但如果有复数角色，只有一人用 CSV 设定会造成混乱，所以稳妥的做法是全都在 ERB 侧添加。  
如果是主人公选择式，先删除 0 号角色，再添加其他角色。  
对于那种各自由 AI 行动类型的游戏（如 era 红魔馆、era 恋姬等），即使没有成为同伴或奴隶也需要角色数据，所以机制是一开始全员 `ADDCHARA` 创建数据，只显示需要的部分。

### 不要附带 emuera.config  
如果在分发文件中包含 `emuera.config`，在版本升级时会覆盖玩家自定义的设置。  
但如果没有任何设置，布局等往往会大幅崩坏，所以利用 [_default.config](../Emuera/config_files.zh.md) 的机制会很方便。  

具体步骤大致如下：  
如果不改变选项进行更新，只需执行 (4) 即可。  

1. 正常设置成自己喜欢的样子，生成 `emuera.config`  
2. 将 `emuera.config` 复制到 csv 文件夹，重命名为 `_default.config`  
 （如果是派生变体等情况，原本就有 `_default.config` 的话，将其删除或改名）  
3. 删除与 exe 同文件夹下的 `emuera.config`，确认在该状态下启动、保存、加载没有问题  
4. 此时 (3) 中应该已经生成了 `emuera.config`，再次删除 `emuera.config` 并压缩成 zip  

如果是会导致完全无法运行（而不仅仅是外观崩坏）级别的设置，建议在 csv 文件夹中创建 `_fixed.config`。  
例如 `_Rename.csv` 或 `_Replace.csv` 的设置就适合放在 `_fixed` 中。  
虽然通常不会去改那些选项，光有 default 也可以，但在大幅版本升级等中途改变了设置，且该设置是必须的情况下，请使用 `_fixed.config`。  

如果是不想设为 `_fixed` 但又重要的选项改变了，请告诉玩家“暂时删除 `emuera.config` 后再玩”。  
（站在玩家立场，如果版本升级后出现异常，应先尝试删除手头的 `emuera.config` 确认能否运行，然后再向作者报告）  

窗口宽度和高度对某些变体来说超重要，但最好不要设为 `_fixed`。  
因为经常有人改变字体种类和大小，并调整画面尺寸来游玩。

### 文件名要通俗易懂  
- 视作解释文件的一行注释  
- 新添加的文件推荐使用日语  
- 如果是从派生源继承的文件，且功能特别没有变更，保持原样即可  
- 如果中途改了名字，不要以补丁形式，而是分发整体  
- 如果纠结文件名，可能是函数塞得太多或缺乏统一感，考虑是否应该拆分文件  
（如果连拆分到一个函数都纠结，可能是把一个函数塞得太满了）  

eraRorona 的文件命名方式非常有参考价值。  
例如调教相关文件夹，通过在开头添加数字来对齐文件排列顺序，按执行顺序或场景进行整理。  
虽然文件夹分类也有效，但分得太细会导致文件难找，此时在开头加数字的管理法很推荐。在执行顺序难以理解时也有效果。  

另外在 `ABL` 或 `Chara.csv` 中，通过将传统名称与说明用 `_` 连接，既能知道对应传统变体中的哪个文件，又能知道内容是什么。  
对于派生变体中已有文件的重命名，这个方法似乎很好。

### 变量名・函数名的命名法  
- 不使用区分大小写的选项  
- 连接多个英文单词时，用 `_` 代替空格  
- 反复使用的东西用短名字，使用次数少的优先考虑易懂性  
- 如果一下子定不下名字，积极使用日语名字  
- `TALENT` 或 `ABL` 等系统中使用的单词部分保持原样。不要强行翻译成日语  

关于日语名，虽然有过去的心理阴影、切换输入法麻烦、有英语圈人士参与开发等理由而不使用的人，但如果没有这些理由，建议使用。  
过于执着英数字会导致问题，例如因为都是时间关系就做了 `TIME`、`TOKI`、`TIMER`、`TIME2`…等各种名字，事后看完全不知道是什么意思。  
起不懂的名字，再写注释让人懂，这是双重功夫。  
在复杂计算式等地方多次出现同一变量时，名字太长会很麻烦，所以有时优先短小和易写性。  

另外，Emuera 的大小写选项只对半角字符有效，对全角字符无效，请注意。除非是游戏中的专有名词，否则稳妥起见不要在变量名中使用全角字母。

### 消除魔术数字 (Magic Number) { #_6 }

- **最好改写的数字**  
- 与内容无关的整理编号（如角色、素质等）  
- 具有特殊意义的数字（如上限值）  
- 多次出现且含义相同的数字  
- **可以保持原样的数字**  
- 数字本身具有意义的（如第几个）  
- 用于变量或常数初始化的数字  
- **难以判断的数字**  
- 初始值、最小值  
- 仅在该函数内使用、只使用一次的数字  
- `[200]～` 这样的命令编号  

编程中所说的**魔术数字**，是指只看数字不明白其含义、没有注释就看不懂的东西。  

在 era 中，例如为了参照技巧的值而写了 `ABL:2`，这个 `2` 就是魔术数字。  
只知道这是在 `ABL.CSV` 中定义为第 2 号的能力，而且不同变体定义不同，根本上 `2` 这个数字与“技巧”毫无关系。  

在显示相关等处，有时“第 2 个”本身有意义，而“是技巧”这件事没有意义。这时应该写 2。写成技巧反而会让含义变得模糊。  

主要的改写方法有以下 3 种：  
- 像 CSV 表記那样写，如 `ABL:技巧`  
- 创建常数 [#DIM CONST](../Emuera/user_defined_variables.zh.md)（也可以用变量或表达式函数）  
- 也可以使用 [`#DEFINE`](../Emuera/ERH.zh.md)，但处理困难，面向高级用户。  

例如角色的最大人数，假设是 100，如果在各处都写 100，看到的人无法立刻明白这是最大人数。  

``` { #language-erb title="ERB" }  
#DIM CONST 最大人数 = 100  
```  

像这样写在 ERH 中，以后想改人数时很简单，用 GREP 搜索“最大人数”也能轻松查出使用位置。  

最大值相关的最好都做成常数，但最小值视情况而定。  
制作 `FOR` 循环时写 `#DIM 最小人数 = 0` 并不会增加易懂性。  
但是在跳过 0 号“你”而从 1 开始的 `FOR` 循环时，是否将这个 `1` 做成常数就令人纠结了。  

``` { #language-erb title="ERB" }  
#DIM CONST 除去你的开头 = 1  
```  

这样写也可以，但或许不如不用 1，改为从 0 开始的循环，仅在 `== MASTER` 时 `CONTINUE` 来得自然。  

关于命令编号，请在 `PRINT` 部分和 `IF` (`SELECTCASE`) 部分保持统一。如果要把条件部分做成常数，选项的显示部分也要用 `PRINTFORM` 等使用相同的常数。只做一边没有意义，还会让人深究是否有特殊意图。

### 魔术数字的变更例（角色指定）  

在使用 `ADDCHARA` 或 `GETCHARA` 指定角色时，由于 Emuera 侧没有对应功能，容易作为魔术数字残留在源代码中。  
在商店买角色时直接用销售编号没问题，但在事件相关中需要指定角色时就必须用到编号。  

目前在 Emuera 中，能用名字指定角色的只有 `RELATION` 数组。其他全部都是编号指定，虽然最终都会变成数字，但中途过程可以下功夫。  

思路主要有两种模式：  
- 使用 `_Rename.csv` 或 ERH  
- 使用 `GETNUM`  

**1. 创建对应常数的方法**  
在 eraMegaten 中，通过 `_Rename.csv` 制作角色名与编号的对照表，运行时替换为该角色的编号。  
可以写成 `ADDCHARA [[キャラ：アメノウズメ]]` 这样。  
比编号更易读，且如果有拼写错误会在启动时发出警告，非常方便。  
缺点是方括号有点碍事，且准备 CSV 很麻烦。  

关于准备，eraMegaten 制作了生成用的 ERB，用 `PRINT` 语句显示 CSV 内容或 `TRYCALL` 所需的数据，保存日志后即可作为 `_Rename.csv` 使用。  
因为如果手工做，在那个阶段必然会发生拼写错误或忘记添加等失误。特别是 `_Rename.csv` 不能分割文件，如果每个补丁单独添加会很麻烦。用 ERH 创建常数时也一样。  
如果人数少，手动也没问题。通常需要指定名字的角色不多，所以也有只写最低限度必要部分的方法。  

另外常数化全般的问题是，拼写错误会被检测出，但如果误以为是另一种类的常数则不会报错。  
例如在 `GETCHARA` 中错误地写了建筑物名，碰巧检查了同号的角色，或者变成必定不在的状态，都不会报错。  
这点无论如何都比不上官方功能的名字表記。  

**2. 用 GETNUM 的 NAME 指定的方法**  
需要 Emuera ver1.819 以后。  
例如在 eratoho 中，写 `GETNUM(CALLNAME, "灵梦")` 就能取得灵梦的编号。  

虽然没怎么见过实际用例，但理论上这两者可以并用。  
例如用 `_Rename.csv` 将 `[[灵梦]]` 替换为 `"灵梦"`，写成 `ADDCHARA GETCHARANO([[灵梦]])`，就可以在启动时和执行时都进行严格检查。  
只不过最初的准备很麻烦，所以只用其中一种就足够了。  
第 2 种不需要准备等，仅需更新本体即可使用，所以推荐。

### GREP 的使用方法 { #grep }
在调查 bug 原因或研究派生源的机制时，GREP 搜索几乎是必须的。  
GREP 功能标配于 Sakura Editor 和 VSCode。Sakura Editor 按 Ctrl+G，VSCode 从侧边栏的搜索菜单进行搜索。  

搜索有直接搜索普通字符的模式，和使用称为**正则表达式**的特殊记法的查法。  
例如想特定使用 `FLAG:100` 的地方，普通搜索会命中 `TFLAG:100` 和 `CFLAG:100`，但如果用正则表达式 `[^TC]FLAG:100` 这样写，就能只查找前面没有附 `T` 和 `C` 的 `FLAG`。  
`[^TC]FLAG:10[0-9]` 的话，会命中 `FLAG:100～109`。  
详细语法请参阅正则表达式的解说网站等。  
如果量少，比起思考正则表达式，往往普通搜索用眼睛找更快。总之方法不限，能找到就行。  

接下来是查找方法，基本是以下 3 种模式：  
1. 用变量名或函数名搜索  
2. 搜索评论中可能写有的关于想调查事项的词语  
3. 搜索在想调查的时机画面上显示的文字  

1. 如果知道使用的变量或函数，单纯搜索其名，使用该处的列表就会哗啦一下出来。  
 巧妙使用正则表达式，也可以区分搜索使用该变量的地方和改写该变量的地方。  
 即使知道对象，如果是 `LOCAL` 或 `A` 等，这个方法就行不通。易懂的变量名也是易搜索的变量名。  

2. 想找与“爱慕”或“妊娠”相关的机制时，搜索该单词大体就能找到。  
 查找画面不出消息的部分也是用这个方法。  
 这个方法的缺点是，没写评论就不行，而且与变量名等不同，如果有表記差异就搜不到。即使有评论，如果不写“妊娠”而写“怀孕”或“懐妊”就找不到。  
 写评论时也要考虑到搜索时的情况，否则连自己都找不到。  

3. 这个稍微需要点窍门。因为画面显示的内容可能是程序或 `PRINTFORM` 格式化后的结果。  
 调查胸部变大的处理所在的变体时，搜索  
 `＜○○○的胸部变大了＞`  
 这样的消息，绝对出不来搜索结果。因为 `○○○` 部分随角色而异，ERB 中不会直接写这样的文章。  

 这种情况下要把单词切碎来查。第一候选是 `胸部变大了＞`，但假如胸和屁股是共通机制，这也可能不行。“大”和“小”也可能由程序处理。  
 什么都搜不到，或者搜到的都是不对的东西时，就尝试 `变大了`、`大`、`胸`、`了` ……这样逐步试下去。  

 如果切碎也不行，就用其前后文中能搜到的东西来搜。如果那篇文章附近有 `CALL`，就去看看 `CALL` 的前方。这样追踪流程一定能到达。

### 关于调教命令的执行判定差异  
1. 显示且可执行（普通的）  
2. 显示但不可执行（对象的干劲或 `PALAM` 不足）  
3. 不显示也不可执行（道具不足、性别不同、肛门太窄等）  
4. 不显示但可执行（派生命令）  
5. 无论如何都无法执行（bug、制作途中、平衡崩坏被无效化等）  

调教命令分为这 5 类，根据自己或对方的状况变化。  

稍微难懂的是 (2) 和 (3) 的区别，同样是不可执行的命令，有显示和不显示的区别。  

基本上 (2) 是执行值不足，执行值是将调教对象的干劲数值化的东西。  
通过提高欲情或润滑，执行值会变动，所以在该时间段的调教中也有可能变得可执行。  
例如自慰不需要特殊技术，但本人没有干劲就做不了。（从这边做的话变成爱抚）  
口交如果没有同意就会变成逆强奸的形式，或者被咬。  
有的情况只提示不可执行和所需执行值就结束了，但也会有拒绝口上出现或伴随体力减少。  
也有执行值判定有多个的变体，同样是执行，是强行进行还是获得同意后顺利进行会有所不同。  

(3) 是道具不足、ABL 不足等，总之在该次调教中看起来做不到的归为此类。  
通过 ABL 上升或购买道具等，只能在调教后满足条件，满足后从下一次调教开始可用。  
在人选命令的选项画面进行显示切换时也能用到。  

(4) 的派生命令，是通过组合特定命令实现的隐藏技巧般的存在。  
许多变体采用了连续进行舔阴和口交变成 69 等机制。  
原则上 3 个以上的命令也可以，但大多是前一个命令 (`PREVCOM`) 与当前命令这两个组合发动。  
不愧是隐藏技巧，效果通常比普通命令强力。  

(5) 曾在命令过多时使用，但最近多在选项画面设定，以该 flag 为条件用 (3) 的机制使其不显示。  

根据变体方针或作者喜好有所不同，但大体是这种分类。  
即使是奉仕系，难度高的如果 `ABL:奉仕精神` 等不足就是不显示的 (3)，显示后也需要高执行值的命令也有。  

命令的显示条件是以下两点：  
- 记载于 `Train.csv`  
- 对应的 `COM_ABLE◯◯◯` 函数返回值为 1，或者根本没有 `COM_ABLE◯◯◯` 函数  

始终是 (1) 的情况只需写在 `Train.csv`，不制作 `COM_ABLE◯◯◯` 即可。  
(2) 可以在 `COMF◯◯◯` 中执行值不足时返回 `RETURN 0` 来制作。  
(3) 制作 `COM_ABLE◯◯◯`，在其中检查是否可执行。  
(4) 的派生命令未记载于 `Train.csv`，或在 CSV 内被注释化。如果能派生，在派生源命令的开头使用 `JUMP COMF◯◯◯`。  
(5) 在 CSV 中注释化，如果没有派生用的 `JUMP`，在 `Train.csv` 中去掉 `;` 就能变成可用命令。  

eraMegaten 的情况下，如果执行会变成派生命令，即使在一览中也显示派生先命令名的机制，但这在标准命令显示中做不到。  
因此让 `COM_ABLE◯◯◯` 返回 0 使通常命令一览无效，用 `@SHOW_USERCOM` 全部显示。  
（准确说是，仅在 `CALLTRAIN` 命令时从 `COM_ABLE◯◯◯` 调用条件检查用的函数，其他情况无条件返回 0 的机制）

### 关于小数的计算、显示  

erabasic 中除了 `TIMES` 命令这一例外，没有处理小数的机制。  
即使使用 `TIMES`，也不能作为参数传递，所以如果实际处理在别的函数中进行等情况就不适合。  

但实际上，即使是没有使用 `TIMES` 的变体也在进行小数计算。  
例如角色间的相性 (`RELATION`) 值，这是表示倍率的，如果用小数写，100% 对应 1.00，1% 对应 0.01。  
怎么计算呢？就是乘以放大了 100 倍的数字，然后将结果除以 100。  

``` { #language-erb title="ERB" }  
UP:4 *= RELATION:R  
UP:4 /= 100  
```  

大多数变体的 SOURCE 相关中都包含这样的代码。  
先直接乘以与调教对象的相性值，再除以 100，得出 `UP:4 * 相性 (%)` 的计算结果。  
通过以 100 倍的状态进行计算，可以用整数实现 100 倍的精细度计算。  

不仅计算，显示也可以做成小数。  
想显示 `280.56` 这样的小数时，内部保存和计算使用 `28056` 这样的整数，仅在显示时加工得像那么回事。  

``` { #language-erb title="ERB" }  
LOCAL = 28056  
PRINTFORML {LOCAL/100}.{LOCAL%100}  
```  

除以 100 的商 280 作为整数部，放入小数点，除以 100 的余数 56 作为小数部……这样显示，玩家就会认为是 `280.56` 这个小数。  

这称为**定点数**方式，只要有整数和乘除（及取余）计算就能使用，所以在没有小数功能的 era 中也常用。  
和百分比显示一样，用熟悉的 100 倍计算的情况很多，但如果是 0.1 刻度乘 10 倍就行，想指定 0.001 单位就必须乘 1000 倍，需要更细的数字就不断增加位数。  
不过，用定点数增加小数位数意味着减少整数部的位数，所以在可能有亿、兆等巨大数字的计算式中，请不要过度增加小数部。  

不习惯时会出现与预想不同的结果，特别是位数错位。  
例如如果被乘数和乘数都放大了 100 倍，结果就是原来的 10000 倍，即使除以 100 也还是 100 倍的数字，变得奇怪。  
加减法的情况下，必须用相同倍率的数字之间进行计算。  
如果觉得位数明显不对，请用计算器对比计算结果进行调试。  

另外，不仅限于定点数或 era，在挂和除无论谁先结果都一样的计算中，请**先做乘法，再做除法**。  
除了能处理分数的编程语言或高性能计算器外，计算机计算如果先做除法，因舍去产生的误差会导致结果不准。  
`1000*3/3` 是 1000，但 `1000/3*3` 的计算结果是 999。

### 关于 IF 条件式的深入说明  
`IF` 结构通常与 `==` 或 `>` 等比较用的条件式配套使用。  
如果符合条件就照常执行，否则执行 ELSE 部分，若无 `ELSE` 则从 `ENDIF` 紧接着的地方重新开始程序。  
但是，在看各种变体的代码学习时，有时会看到仅凭这些无法解释的、不可思议的 `IF` 语句。  

准确地说，`IF` 检查的是**条件式的计算结果是 0 还是非 0**。  
所以，即使写下面的程序也不会报错，会根据当时 A 的值进行分支。  

``` { #language-erb title="ERB" }  
IF A  
     PRINTL A 不是 0  
ELSE  
     PRINTL A 是 0  
ENDIF  
```  

这与写下述情况结果相同。  

``` { #language-erb title="ERB" }  
IF A != 0  
     PRINTL A 不是 0  
ELSE  
     PRINTL A 是 0  
ENDIF  
```  

像 `==` 或 `!=` 这样的比较条件式，是条件一致时变为 1，不一致时变为 0 的计算式。条件一致时，因为它不是 0，所以在 `IF` 语句中也会按计划判定。  
除了 `IF` 语句，`WHILE` 或三元运算符等根据条件分支的机制全部都是这样。  

作为条件判定结果的 0 称为“假 (False)”，0 以外称为“真 (True)”。如果用开关比喻，真是 ON，假是 OFF。  
就像“如果 `A>5` 为真的话～”这种感觉。  
真・假的叫法不仅是 Emuera，而是编程通用的叫法。  

**比较是计算，结果是数字**，这也适用于条件分支以外的情况。  
下面是直接将条件结果用于代入的例子。  

``` { #language-erb title="ERB" }  
     A = 5  
     B = A == 5  
```  

这种情况下，A==5 的结果是 1，所以 B 的值是 1。  
如果用 IF 语句写就是这样：  

``` { #language-erb title="ERB" }  
     A = 5  
     IF A == 5  
          B = 1  
     ELSE  
          B = 0  
     ENDIF  
```  

应用这个机制，在检查复杂条件时，也可以分成几个式子进行计算。  

``` { #language-erb title="ERB" }  
     A = TALENT:处女 == 1  
     B = ABL:技巧 > 3  

     IF A && B  
          PRINTL (TALENT:处女 == 1)&&(ABL:技巧 > 3) 为真的情况  
     ENDIF  
```  

大多数情况下正常写条件式最易懂，但因为代码容易变长，为了省去冗余，有时会使用乍一看难懂的 `IF` 语句。  

Emuera 的条件判定机制是 C 语言风格的，其他编程语言大体思路相同，但在细节部分有所不同。  
例如 Emuera 中比较结果是整数，但也有准备称为布尔型（逻辑型）的与整数不同的机制的语言，那种语言中不能将比较结果代入整数。  
学习其他语言时，请查阅手册确认该语言如何处理“真”、“假”。

### 基于二进制的位操作 (`STAIN` 的机制) { #2stain }
- 可以在一个变量中塞入大量 flag  
- 如果出现 `&` 或 `|` 大体就是这类相关  
- 现在要用的话请用 SETBIT・GETBIT  

在 erabasic 的机制中，`STAIN` 是相当难懂的机制。  
这是通过将 1 个整数变量分解成许多小数字，来制作大量简单 flag 的方法。  
除了 `STAIN` 以外也能在其他地方见到。  

例如想用 0～9 的数字 6 个时，普通做法是使用有 6 个变量的数组，但也有将 `406478` 这样的 6 位数字看作 6 个 0～9 排列的方法。  
想查千位的数字时，可以先转成字符串查右数第 4 个字符，或者用整体除以 10000 的余数再除以 1000。如果工夫计算，也可以只改写瞄准的那一位数字。  
整数最大 19 位，但在全位填满 9 的范围内是 18 位，所以用这个方法可以塞入 18 个 0～9。相应地所需变量数减少，存档数据也能变小。  

标准的 `STAIN` 情况下，不需要 0～9 的范围，只要区分有无污垢即可。  
那样的话只要有 0 和 1 就行，所以如果不看作 10 进制而看作 2 进制（每 2 进一位），似乎能做出比 10 进制分隔更多的 flag。  

把每 2 进一位的思考方式称为**二进制**，用二进制思考方式写出的数字称为**二进制数**。  
`Emuera` 中准备了在开头加 `0b` 来写二进制数的写法。  
（变量名等有不能以数字开头的规则，所以不用担心与以 0 开头的二进制数冲突）  

原本计算机内部装置全是按二进制运作的，但在显示等时转换成了十进制，所以通常人类无需意识二进制。仅在特殊情况下以二进制状态处理。  
我想在 era 变体中使用二进制，仅是在像 `STAIN` 那样想在一个变量中塞入多个数的时候。  

每 2 进一位可能很难想象，可以想象成只有上面珠子的算盘。也可以看作是 ON/OFF 开关的集合。  
（通常的算盘是二进制的天珠和五进制的地珠组合，桁整体是十进制机制）  

重要的是，十进制数和二进制数只是写法和思考方式的问题，作为数值是完全相同的。就像写 1、写壹、写 ONE 都表示同一个数一样。不是像正负那样的不同数值。  
内部也不与普通整数区分，所以在程序上即用二进制写代入的变量，用 `PRINTV` 等文字显示时也会以十进制显示。`PRINTV` 严格来说不是将指定变量显示在画面的命令，而是将指定变量以**十进制**显示的命令。  
如果想为了调试以二进制在画面显示，请用 `CONVERT` 函数转换后用 `PRINTS` 等作为文字显示。  

二进制每 2 进一位，所以不像个十百千万那样每桁乘 10，而是乘 2 增加。  

| 十进制 | 1 | 2 | 4 | 8 | 16 | 32 | 64 | 128 | 256 |  
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |  
| 二进制 | 0b1 | 0b10 | 0b100 | 0b1000 | 0b10000 | 0b100000 | 0b1000000 | 0b10000000 | 0b100000000 |  

记住常用模式很方便，但不可能记住所有模式。如果把 Windows 计算器设为程序员模式，就可以在二进制和十进制间相互转换，请利用这个查需要的数。  

二进制中不能说个位、十位、百位…，所以称为**第几比特 (bit)**。  
比特 (bit) 就是二进制中的位。Emuera 的整数是 64 比特，也就是相当于 64 个 flag。  
Emuera 中将二进制写时的右端作为 0 比特，向左数是 1 比特、2 比特…，左端是 63 比特。  

各桁的取出也可以用与十进制相同的计算，但通常使用动作高速且写得简洁的**比特掩码 (Bitmask)**。Emuera 中 `&` 运算符相当于 `AND`，`|` 运算符相当于 `OR`。  
[关于污垢 (页面下方)](../eramaker/variables.zh.md)  
[Mask (信息工学)](http://ja.wikipedia.org/wiki/%E3%83%9E%E3%82%B9%E3%82%AF_%28%E6%83%85%E5%A0%B1%E5%B7%A5%E5%AD%A6%28)  
[eratoho 总结 V3 - ERB 语法讲座 3](../manual/eratohowiki-ERBmanual.md#_38)  

顺便提一下 `&&` 和 `&` 的区别，`&` 是数值本身的 `AND`，`&&` 是将两侧转为 1(真) 或 0(假) 后的 `AND`。  
`A && B` 与 `(A != 0)&(B != 0)` 是一样的。  
通常使用 `&&`，仅在作为比特掩码使用时使用 `&` 应该就没问题。反过来说，写有 `&&` 就是普通条件式，写有 `&` 就是比特掩码相关。`||` 与 `|` 的关系也一样。  

旧的比特掩码程序，仅将十进制部分改写为二进制就会相当易懂，但现在可以用 `GETBIT`、`SETBIT`、`CLEARBIT` 这 3 个命令简单进行比特操作。  
除非需要一次性取出多个比特，否则不需要比特掩码。（这里与其说是实用，不如说是为了变体改造的知识而写）  
[BIT 操作系命令](../Reference/BIT_OPERATION.zh.md)  

这种方法的塞入缺点是，后来需要 64 个以上的 flag，或者想设定 1 以上的数时，应对很麻烦。不能像数组那样简单增加上限。  
最近的 Emuera 也可以用 `#DIM` 追加变量，所以那种情况可能更简单。

### 角色固有能力编号 (ID) 的制作方法  
eramaker 原本没有拥有相同 `NO` 的角色，但随着像 Megaten 那样同种族的角色能成为多个仲魔，或添加随机角色，变得需要 `NO` 以外能特定该角色的信息。  

例如别篇文章中妊娠时的双亲信息，或在 `SORTCHARA` 中对 `MASTER:0` 和 `TARGET:0` 以外的编号进行排序后追踪时所需的信息。  

常被称为角色 ID 或 ID，本文中就称为 ID。  
目前 eramaker 或 emuera 的系统没有准备，所以必要的变体各自保存在 `CFLAG` 中，或做成可用函数获取。  

| 变体名 | ID 保存场所 | 上限 | 机制 |  
| :--- | :--- | :--- | :--- |  
| eraMegaten | `CFLAG:角色固有编号` | 200 (保有上限) | 不与现有角色重复的最小数 |  
| eraRorona | `CFLAG:角色 ID` | 生成时的 CHARANUM | 不与现有角色重复的最小数 |  
| eraWeapon | `CFLAG:3109` | 整数上限 | 计数器每次加 1 |  

其他变体也大体接近这三种方法之一。  
也有很多不是 `CFLAG` 而是做成可用 `@GET_ID` 函数获取的。  

Megaten 和 Rorona 基本机制相同，思路是只要不与现有其他角色编号重复即可。  
这个方法对排序后的追踪足够，但如果继续游玩，当然会出现 ID 相同的角色，如果用这个 ID 做血缘关系等，后来数据显示的不是数据不详而是别人。  
需要不做那种用法，或删除角色时消除对该角色 ID 的引用等对应。  

Weapon 或恋姬等采用的是单纯按制作顺序赋予 1 开始的通号的方法。  
可能会担心“迟早会到极限报错吧？”，粗略计算一下“迟早”是什么时候：  

```  
9223372036854775808 / (100000000 * 60 * 60 * 24 * 365) = 2924  
```  

Emuera 的整数值上限是 922 京，所以除非每秒生成 1 亿角色连续 3000 年，否则 ID 不会用完。  
现实地考虑，1 秒生成 1 亿内存就不够了，而且在坚持 3000 年前 PC 早就坏了。普通考虑在编号用完前年份显示 4 位就不够用了。  

固定上限循环使用的优点是，在用角色变量以外的数组管理数据等情况。  
例如放入角色间相性的数组，无法做成 922 京×922 京的二维数组，所以必须用现实的数值制作。  
需要考虑不以数组排列顺序，而是以放入数组的 ID 来管理读写等。  

如果没有特别理由，推荐 Weapon 方式。是最简单的方法，以后想下功夫时也容易应对。  
如果觉得找 `CFLAG` 的空位麻烦，也可以用 `#DIM CHARADATA` 制作专用变量。  

并且 ID 请从 `1` 开始而不是 `0`。因为是 0 的话无法与 ID 设定遗漏区分。（Weapon 和恋姬也是 ID 从 1 开始，大概是同样理由）  
后来追加 ID 机制时，也不用在意存档数据的版本，只需自动给 ID 为 0 的角色分配 ID 即可。  
在创建角色时，不要直接使用 `ADDCHARA` 或 `ADDVOIDCHARA`，务必经过自制函数，在其中进行 ID 设定，就不容易发生遗漏。

### 角色列表的分页  
人数多的变体中，角色选择画面放不下，所以这类变体附有分页功能。  
一般称为页面导航 (Page Navigation) 或分页 (Pagination)。  

用于从保有角色中选择调教对手或助手、显示状态的对象，或选择购买角色等。  
这里主要以保有角色为主来写，但购买时的处理机制相同。  

先介绍现有变体的例子可能更易懂，举几个例子。  
这里说的“角色编号”是指 `TARGET` 或 `ASSI` 指定的、当前角色的排列顺序。与 `NO` 不同。  

- **eraMegaten 的情况**  
- 任何场面每页显示 20 人  
- 单字母变量 `A` 代入显示人数，将显示的角色编号代入 `Q:0` 到 `Q:A`，页码代入 P，使用 `SHOW_CHARA_LIST` 命令  
- `@SHOW_CHARA_LIST` 中根据 `A`、`Q`、`P` 的内容显示  
- 显示内容的差异用 `FLAG:商店命令` 分支  
- 如果 P 大于 1 则显示前一页，如果 P 小于 `(人数 -1)/20` 则显示下一页  
- 如果页面变更则改变 P，A 和 Q 不变重新执行 `SHOW_CHARA_LIST`  

- **erainSchool**  
- 每页显示 10 人  
- 在 `@DISPLAY_COMMON` 中进行显示和分页  
- 根据调用场面不同，作为 `DISPLAY_COMMON` 的参数设定  
- 根据调用场面不同的部分做成别函数，用 `TRYCALLFORM` 调用  
    （调教选择时是 `@DISPLAY_SET01_FUNCTION`，助手变更时是 `@DISPLAY_SET03_FUNCTION` 等）  
- 用 `REPEAT CHARANUM` 循环，不显示的角色 `CONTINUE`，页面范围外的角色不显示但不 `CONTINUE`，仅显示范围内的角色  
- 如果显示位置不是开头则显示“返回前一页”，如果从显示位置起还剩 10 人以上角色则显示“进入下一页”  

还有其他细微机制，但大体是这种构造。  

无论哪种方式，必要的规格是决定每页人数。  
取决于想定画面尺寸和上下显示的东西，但如果是 1 列 1 角色方式，大概是 10～20，最多 30 人左右吧。  

其次是区分显示和不显示的角色。  
例如设定每页 10 人，第 24 号角色通常应显示在第 3 页。  
但如果 24 号之前的人因某种理由不显示，可能是第 2 页，也可能是第 1 页。仅靠角色编号无法计算。  
或者变成第 1 页 4 人，第 2 页 8 人等，每页人数参差不齐。  
避免这个问题有 3 种方法：  
- Megaten 式：准备仅填入了要显示编号的数组  
- inSchool 式：包含不显示范围的角色每次都检查  
- `SORTCHARA`：将要显示的角色排在开头侧  

同时也调查各自最多显示多少人，用于计算最大页数。  
推荐 Megaten 式，但像 Q 这样的全局变量用于函数间传递不好，最好在 `ERH` 中用 `#DIM` 制作专用变量，或做成用参数传递的机制。  

条件和显示内容随场面不同与无分页时相同，可以用 `SELECTCASE` 或 `IF` 分支，或做成别函数。  
也有变体制作字符串的条件列表传递。这样优点是仅看调用部分就知道条件。  
感觉是在 erabasic 可能的范围内，各自工夫做出了相当于其他语言的匿名函数或接口继承的想法。  
几乎没区别的话 IF 也可以，但如果场面不同显示内容完全不同，或显示种类多，别函数可能更好。  

返回前一页很简单，第 1 页不显示，其他显示即可。  
不过需要确认第 1 页数字上是 0 还是 1。  
这里暂且按第 1 页是 1 来谈。  

是否进入下一页，在当前页码×10 小于总件数时，或当前页码小于最大页数时显示。  

像购物网站那样做成 `1.2.3.4.5…` 飞到任意页面也是可能的。稍微有点麻烦。  
如果是其他编程语言用的，网上应该能找到制作方法。  

像页面导航这样的机制，如果搞不好了，先缩小规模，边写在纸上一边测试比较好。  
例如页数计算，先做成每页 3 人或 4 人这种心算能搞定的紧凑东西。  
然后写出人数 4 人是几页？5 人又怎样？的计算结果或想显示的结果，头脑就会整理清楚。

### 用 SORTCHARA 进行复杂的排序处理  
通常是按 `ADDCHARA` 顺序排列的角色变量，但人数多了就想按各种条件排序（Sort）。  
这种情况下可以用 `SORTCHARA` 命令高速排序。  

通常用法像 `SORTCHARA MAXBASE:0` 这样，按角色变量的大小顺序或小顺序排列。  
如果这样就能符合自己喜好还好，但如果条件指定无法用一个变量解决，就不能直接使用。  

**第 1 种方法**是分成多次 `SORTCHARA` 使用。  
1. 按条件 1 排序，条件 1 相同的情况按条件 2 排序  
2. 按条件 1 排序，符合条件 2 的东西排在列表下方  

这种情况下用 2 次 `SORTCHARA` 就能解决。  
`SORTCHARA` 是所谓的**稳定排序**机制，排序时如果数字相同则保持原来的排列顺序。  
因此 (1) 的情况，按 "`SORTCHARA 条件 2`"、"`SORTCHARA 条件 1`" 的顺序执行，仅在条件 1 相同的情况下，条件 2 的排列会保留。  
(2) 的情况按条件 1、条件 2 的顺序 `SORTCHARA` 即可。不过只有 0 和 1 的素质等这样就行，但像顺从 3 以下这样的细致指定做不到。  
如果按顺从排序，1、2、3 会分别排好，变成非意图的排列顺序。需要并用后述的方法。  

**第 2 种方法**是计算条件放入角色变量中。  
例如刚才的顺从 3 以下的话题，在排序前检查全角色的顺从是否 3 以下，放入角色变量就能解决问题。  

``` { #language-erb title="ERB" }  
FOR LOCAL, 0, CHARANUM  
     ;实际使用时不用 777 而用未使用的编号，或用 #DIM CHARADATA 制作新变量  
     IF ABL:LOCAL:顺从 <= 3  
          CFLAG:LOCAL:777 = 0  
     ELSE  
          CFLAG:LOCAL:777 = 1  
     ENDIF  
NEXT  
```  

在此基础上 `SORTCHARA CFLAG:777`，就能清楚分离顺从 3 以下和比那大的角色。  
像按体力和气力的合计值排序这样的复合排序，  

``` { #language-erb title="ERB" }  
CFLAG:LOCAL:777 = MAXBASE:LOCAL:体力 + MAXBASE:LOCAL:气力  
```  

像这样改变计算式就能应对。  
更复杂的，例如出售价格之类的也一样。  

多次 SORT 和事前计算可以同时使用，就能实现想要的排序。  

如果想让人手动排序，有用 `SWAPCHARA` 一个一个排序的方法，但那之后如果用 `SORTCHARA` 手动指定部分会变。  
如果内部不得不使用 `SORTCHARA`，需要在排序前将那时的顺序保存到变量，用完再还原，或者不做排序而采用指定优先角色的方式等，需要下功夫。

### 一览显示 CSV 中有的角色  
**Q.** 想把主人公做成选择式，但角色列表弄不好。  
**A.** 利用 `CSVNAME` 或 `CSVABL` 等，可以获取记载在 CSV 中的内容。  
 另外通过 `EXISTCSV` 可以获取任意角色编号的 CSV 是否存在。  
 一边使用它们一边适当循环吧。  


常用于角色购买或选择。  

下面的例子是编号一览显示 CSV 注册的角色名。  
即使中途有缺号的角色，因为事先用 `EXISTCSV` 检查了，所以不会显示奇怪的东西。  
话说回来，即使把上限设为 10000 人也只是动作变慢没意义，所以这里暂定检查到 99 号。  

实际使用的案例中，大多一起处理隐藏角色或不可选角色的不显示、参数或金额的显示等。  
（这次例子中如果把隐藏角色设在 100 号以后就能简单做成不可选）  

``` { #language-erb title="ERB" }  
FOR LOCAL,0,100  
    IF EXISTCSV(LOCAL)  
        PRINTFORMLC [{LOCAL}]%CSVNAME(LOCAL)%  
    ENDIF  
NEXT  
```  

这个例子的 100 是魔术数字，实际使用时建议参考“消除魔术数字”进行改写。

### 制作随机角色  
有几个变体采用了与通常按 CSV 生成角色的系统不同、每次出现不同角色的机制。  
通称随机角色。  
理由各种各样，如原作登场人物不够、想每次玩不一样的等，是很受欢迎的系统。  

制作随机角色时，有从原有 CSV 用 `ADDCHARA` 制作的方法，和使用 `ADDVOIDCHARA` 的方法。  
用 `ADDCHARA` 制作时必须准备随机角色用的 CSV，但优点是大致的设定值可以在 CSV 侧设定。  
例如 eraWiz 的情况，每种职业有不同的 CSV，以此为基础在 ERB 侧进行调整的感觉。  
以前没有 `ADDVOIDCHARA`，所以也有先做个接近空的 CSV 的手法，但现在用 `ADDVOIDCHARA` 就够了。  

然后调整那样制作的角色的体力和参数。  

``` { #language-erb title="ERB" }  
MAXBASE:0 += RAND:200  
```  

这样就变成了 HP 在初始值～初始值 +199 范围变动的随机角色。  
基本是对体力、气力、素质、经验…等重复这样的事情。  

但是完全交给骰子的角色会做得很粗糙。  
例如既有高傲又有低傲，既有乐观又有悲观这样的素质同时存在很奇怪。而且必定拥有其中一个也很奇怪。  
需要地道的工作来调节，使得高傲 20%、低傲 20%、都不是 60%…这样有适度波动，让人感觉不到不自然。  

虽然是喜好问题，当然也有那种粗糙感很好的情况，但那种情况也必须决定粗糙的范围。  
视情况能力封顶的调教完毕角色出来也可以吗？那是百分之几的概率？  
不仅是 era 变体，这也是很多游戏共通的课题，参考有随机角色出来的游戏的攻略 wiki 应该也有帮助。  

名字也有问题。  
50 音完全随机的名字，首先没法正常发音。  
基本机制是在 ERB 中写入几个名字，从中使用不与现有角色重复的名字。  
日本人或中国人的情况，也有随机组合名字常用汉字的方法。  
这也很难输出像样的名字，但至少姓氏和名字分开比较好。  

介绍几个随机角色生成的实例。  
首先是 eraWiz。决定职业之外还决定种族，再加上随机大致性格进行分支，容易附上符合性格的素质。  
“高贵”的角色容易变高傲，“粗暴”的角色容易变反抗等。  
既是符合角色的素质，性格分类又能用在口上，是很棒的东西。  
名字也按性格分开，总共约 200 种。  

其次是 eraWeapon。在不让矛盾素质同时附上的同时，也有根据武器特性容易附上的素质（鞭拟人化则 S 率上升等），是正统的生成处理。  
名字 50 种。因为是自创武器拟人化的设定，推荐自己起名，随机名的数量比其他少。  

其他变体也应该都是“制作基础角色 -> 在合理范围内调整数字 -> 起名”…的基本结构，边考虑这些边读应该容易解读。

### 女儿（儿子）调教功能的制作方法  
（前提是使其可调教，但即使只进行妊娠出産不调教，除角色生成外的机制也是共通的）  

与随机角色思路相同，但多是参照双亲数据制作。  
虽然不是必须，但性格相似、继承了能力的强角色等，比起完全随机，有这些更有氛围。  
变成容易附上与双亲相同素质，或双亲能力的 10% 加到初始值等，加了这种补正的随机角色。  

当然没有随机要素也能做孩子。  
虽然不是 era，但在火焰纹章觉醒或圣战之系谱中，名字和职业按母亲固定，父亲每项升的能力和降的能力固定，没有随机要素。  
也有第一子是固定角色，第二子以后随机的方法。这在历史模拟游戏中多见。  
但前提是生出多个孩子的话，能力都一样很无聊，所以目前 era 变体中似乎没有固定方式。（eraMegaten 的合体接近这个思路）  

关于孩子的性别，有限定女儿的，有选项可变比率的，变体各异。是喜好问题。  

孩子角色让人困扰的是识别父亲的方法。  
多在妊娠角色的 CFLAG 等处记录父亲信息，但如果每个 CSV 只有 1 个角色只用 `NO` 也行，但有随机角色或同一 CSV 有多个角色的情况。  
所以 eraMegaten 中让全角色拥有 `CFLAG:角色固有编号` 这个数字，这个数字每个角色不重复，用于特定父亲。  
口上或妄想中亲属关系也很重要，所以作为角色数据保存，在状态画面也显示父母名字比较好。  

因为有妊娠和出産时期的错位，出産时父亲可能已被卖掉。  
也可以考虑卖掉了也只留数据的方法，但没找到这样实装的例子。  
存档数据会不断变大，角色列表中混入不需要的东西等缺点多，而且那么重要的角色应该不会卖吧，大概是这样的判断。  
eraMegaten 中除了角色固有编号还记录了双亲的 `NO`，如果被卖了就参照那个分配种族等。  

还有临月时的特殊处理、産后的母乳和育儿等，但基本是将妊娠开始后的天数保存在母亲的 `CFLAG` 中，每天结束时检查那个天数，进行消息显示或能力变更来应对。  
也有不是还剩几天，而是持有“几号出産”这样的参数的方法，但这方法与“强 New Game"系的功能相性不好。  
继承时需要重置妊娠信息等应对。  

难的是孩子的年龄设定。几岁开始可调教感觉好？包括双亲一起成长吗？世代交替吗？有人数限制吗？等等。  
如果是成长并交替的模式，不以天为单位而以周或月为单位，不然在成长前就腻了，但太快又可能在充分调教前就寿命到了。  
另外妊娠期间设几 Turn 也是烦恼之处。  
太短的话难以在调教或事件中組み入妊娠 Play 系。  
关系到整体游戏系统和口上等，妊娠系统中最难的就是这个时间设定部分。  

多的模式是缩短妊娠期间，孩子急剧成长并固定在那个状态的时间压缩。  
这样即使原本没有妊娠的变体也能极端的不变换平衡。  
只是不适合一边守护成长一边做爱或年龄差近亲相奸等乐趣。  

全年龄游戏中也有孩子出来的，也可以应用那些做法。  
缩短寿命快速世代交替，或以事件为界限经过年月，或在出産确定的瞬间从未来时间旅行过来等。  

目前还没找到能满足所有愿望的方法。重点思考自己最兴奋的状况来推敲设定吧。

### 调查特定角色是否在奴隶（同伴）中  
在事件发生等条件下，角色是否存在 (`ADDCHARA` 过) 成为条件时，可以用 `GETCHARA` 或 `FINDCHARA` 调查。  

用 `GETCHARA`(角色编号)，可以调查该角色是否存在，如果在的话是从头数第几个。  
如果不在返回 `-1`，如果只需知道在不在，可以用 `IF GETCHARA(角色编号)!=-1` 这样的查法。  

如果条件仅需角色编号 (NO 变量) 就用 `GETCHARA`，但如果用 `NAME` 或 `CFLAG` 等其他条件调查，就用 `FINDCHARA`。  
可以以角色变量中的 1 个为条件，做与 `GETCHARA` 相同的事。  

`FINDCHARA` 作为条件只能指定 1 个变量，所以条件更复杂时，需要自己写处理。  
大概要写 `0～CHARANUM-1` 的循环，逐个检查的程序。

### 希望尽量使用 UTF-8 作为文字编码 { #utf-8 }
SHIFT-JIS 是日语版 Windows 标准的文字编码，但在海外几乎完全不知名。  
即使知道，了解历史缘由的那些事后也不想用吧。  
因此海外制的编辑器中，SHIFT-JIS 的文件无法显示，或部分字变得奇怪。也没有修正的预定。  
即使是日本制的编辑器，内部角落都是日本制的情况也罕见，所以也有难以应对的场面。  

结果现状下能编辑 ERB 文件的软件受到很大限制。  
即使看到海外软件有很好的，制作了 ERB 用的着色设定等，如果是 SHIFT-JIS 的文件也无法好好处理。  
制作 ERB 加工用程序时，必须用对应 SHIFT-JIS 的编程语言制作也是个束缚。  

在那点上 UTF-8 可以说是现在的世界标准。海外制的编辑器和编程语言，只要是 UTF-8 就对应。  
因为编辑器制作常用的基本部件已对应，所以即使各编辑器作者没特别考虑世界对应，也能正常读写。  
Sakura Editor 以前对 UTF-8 的处理也有问题，但版本 2 以后内部以 UTF-8 处理，接近了海外制软件的做法。  
如果想用 eramaker 或旧的 ERB 对应程序没办法，但如果是 Emuera 专用变体，已经没必要转成 UTF-8 了吧。  
随着 UTF-8 普及，各种辅助软件等也变成 UTF-8 专用，制作会变得容易。  

不过制作补丁时最好不要改变文字编码。  
那个补丁追加的部分变得难懂，会让作者和利用者困扰。  
关于追加的文件（而非变更）转成 UTF-8 也可以，但还是在那个变体中统一比较好，混乱少。  

Emuera 似乎只对应带 BOM 的 UTF-8。  
在 Sakura Editor 的保存画面，有写着 "BOM" 的复选框，请勾选那里。  
在选择 SJIS 或 UTF-8 栏的右侧。  
其他工具也大体能选择其中一方。如果是 UTF-8 和 UTF-8N 的选择，**不带 N 的那方**是带 BOM 的。

### 阅读 TRPG 的规则书  
制作游戏系统，就是将脑内设定置换成数字。  
听起来很难，但其逆过程，从数字想象设定，平时在玩 era 时就在做，所以应该没那么难理解。  

研究怎么做最好就是玩游戏，但电脑游戏中详细规则往往不公开。  
即使读攻略本也没写到详细计算公式。  

所以这项推荐桌游 RPG (TRPG) 的规则书。  
书大概 1000 日元左右，其他需要的只有笔具，骰子也可以用智能手机或浏览器用的骰子 App 代替。  
本来是好几个人聚在一起边看规则边玩的游戏，但对游戏系统感兴趣的人来说，作为读物也很有趣。  

有色的 TRPG 也好，不是那样的普通全年龄游戏也行。  
想表现力气大的人和力气小的人所以做筋力值，想表现胸大的人和胸小的人所以做乳尺寸，根本上是一样的事。  
特别是最近的变体，除了调教还有日常生活和迷宫探索等，不仅是色的系统变多了。  
每个游戏每个作者有各种想法，参考那些，做出自己的游戏就好了。  

TRPG 也有很多，举几个推荐的。  

- **剑世界 (Sword World)**  
以正统奇幻世界为题材的 TRPG。  
将实际游玩内容小说化的 Replay 小说很有人气，放在轻小说角落。  
现在书店卖的是大幅翻新的 2.0，但电子书或古本也能买到旧版。  
喜欢老式奇幻的推荐旧版，认为矮人（女）是萝莉角色的推荐 2.0。  

- **Saturn Sphere (サタスペ)**  
以东洋里社会为题材的 TRPG。  
规则中有娼妇和犯罪等要素，参数和技能也有很多那种感觉的。缺点是价格稍高。  

- **绝对隷奴**  
18 禁的 TRPG。与 Battle Fuck 系有点不同，但战斗中打倒对方也行，调教成奴隶也行，是这样的游戏。总之没有色就没干劲的人请用这个。  

- **可免费浏览的规则书**  
图书馆有放的书，但最近网上能看的也多了。  
http://jinriki.tumblr.com/post/60355051949/trpg  
从最新规则的样本，到绝版的旧规则、二次创作物、个人制作的原创等，数量相当多。  
缺点是稍微难读的居多，但数量多容易比较规则，通过比较能明白系统的特征和常见模式等。  

- **视频网站实况的**  
不需要自己玩，但知道怎么玩比较好。边看有趣的视频，容易明白这个数字是这个意思等。  
常看到“Paranoia”或“克苏鲁神话 TRPG"等作品。  

- **eraTRPG 中喜欢的角色出来的游戏**  
因为是调教 TRPG Replay 小说登场角色的变体，出来的角色有 TRPG 的原型。为了提高游玩的充实度，读规则书和 Replay 可能比较好。  
（同一规则有多个 Replay 系列，最好确认是哪本书出来的角色）  

- **知道原作的**  
eraMegaten 玩家的话是真・女神转生 RPG※，动画爱好者的话是 Log Horizon TRPG 等。在知道原型的状态下，更容易明白想用什么样的数字表现什么。  
(※真・女神转生 RPG 是 Night Tail 使用的最新版（魔都东京 200X）目前难以入手。其他绝版规则书也是，出版社出的书应该在国会图书馆可阅览。附近的图书馆有时能帮忙调货，请咨询看看。合不合因人而异，不建议高价买)  

- **Replay 小说有趣的**  
和先读原作再读更容易理解是同样理由，先读 Replay 小说再读规则书更容易理解。  
不知道棒球或足球的人只读规则书大概完全不懂吧。  
小说有趣游戏不一定有趣（当然反之亦然），但情绪会不同。就像有口上就有干劲一样。  
特别是规则书发售后的第一个 Replay，为了初学者说明了技能和步骤等，所以即使没有规则书也大体写得能明白是什么样的规则。  

想在变体中加入战略要素或经营要素的话，不仅 TRPG，桌游也可参考。  
特别是对应 1 人玩的桌游，只要不是特别奇怪的板子，eramaker 应该也能再现。  
（对战用的也能再现，但要做成对战用，或制作相当强的 AI，所以很难）  
FC 或 GameBoy 等复古游戏也不像最近的游戏那么复杂化，容易把握机制。  
这边除了点阵图图形和音乐外，作为游戏系统也能制作类似的东西。

### 不做成 Flavor 要素的方法（做成的方法）  
在 era 变体相关的讨论串中常看到"Flavor"这个词。  
似乎是开始在卡牌游戏或 TRPG 等使用的词，意思是与游玩或规则没有直接关系的要素。  

在 era 变体中，就是指口上或叙述文。除了一部分伴随能力变化的口上，基本是 Flavor Text。有没有参数或得到的珠子数量都一样，但游玩时的感觉会不同。  
像发色这样的要素也偶尔见到，但仅用于想象角色，规则上没有意义。  
关于衣服，有效果的变体和衣服不同可用命令或参数变化有区别的变体两边都有。  

如果是有意做成 Flavor 功能还好，否则那个功能不太被使用，很遗憾。  
另外制作新补丁可能导致传统功能变得无意义。  
这项写不做成 Flavor 的方法。（反过来做就能故意 Flavor 化）  

- **制造差异**  
因为有没有规则上都一样所以是 Flavor，所以要让它有不同。  
例如素质“巨乳”由此可执行命令等不同，但在只有“巨乳”角色出来的变体中，“巨乳”就是 Flavor 素质。因为有那个素质角色间的调教方法或卖价也没变化。  
（派生变体的情况因流用的都合，比起改造系统给巨乳用，给全员加素质更简单）  
没见过“美人”素质，大概是因为不做素质也只会出“美人”吧。有变体为了随机角色加相反魅力素质。“人类”素质也是如果只有人类就不需要，但在 eraMegaten 这样的变体中种族是重要参数。  
“魅力”、“高傲”、"A 敏感”等也容易想给全员加，但做过头角色个性就淡薄了。让素质一定程度分散地制作角色，游玩幅度会变宽，素质也会有意义。  
顺便“处女”素质即使给全员加也不是 Flavor。虽然没有角色间的差异，但有“处女”时和不是时的差异，那件事会影响游玩。  

- **与游戏目的挂钩**  
那个要素是不是 Flavor 根据游戏目的变化。  
游戏目的通常是结局，但也包含多个结局、成就解除等机制。  
例如天数显示，如果有通关条件等天数限制就是规则上重要的显示，但不需要数天数的游戏就是 Flavor 要素。  
玩起来不为钱困的变体中，所持金没太大意义。  
如果想让玩家重视所持金游玩，就要让它关系到通关条件或调教程度。  
也有没什么目的的变体或模式设定，那种情况系统整体就是为了享受情景的 Flavor。  
但即使是模拟城市那样的游戏，也有每一定人口被表扬的成就性机制，以达成实绩 MAX 的 50 万人都市为目标成为动机，所以有什么目标提示或被表扬的事会更像游戏。  

- **根据游玩中的状况改变**  
如果有在所有状况下都优秀的命令或选项，就只用那个，劣的一方就没用的理由了。  
单纯加强劣的一方只是优劣逆转，必定有一方变成 Flavor。  
做成根据状况有利不利变化的机制，就能根据情况区别使用。  
eraKanon 的情况，C 感觉低的角色中 E 按摩器效率压倒性好，但 C 感觉上升的状态下跳蛋的每体力 1 点 C 快感上升值更大。  
（体力气力的消费平衡和 Source 的量也微妙不同）  
eraKanon 中根据素质 SM 系命令比快乐或奉仕更顺利调教，但也有对谁 SM 效果都低（或体力没了）的变体，那种情况 SM 系整体变得难用。  
eratohoA 及派生变体的路线分歧中，通过增加 SM 调教时的卖价，或制作口上分歧，让 SM 有了用途。  

- **附加使用限制**  
即使有其他绝对有利的选项，通过给有利的一方加某种限制，就能制造双方命令都需要的状况。  
例如同一命令的执行效果下降的变体多，这样就有用到 2 个命令的理由。如果检查到 2 个前的命令就是 3 个。  
也有强力命令 1 天只能用 1 次，或使用虽有利但不使用能解除实绩等限制方法。  
没有高价器具或消耗品就不能用也是限制，但如果钱 Flavor 化了就没意义。  
如果玩家判断太强，也会自主进行限制的束缚 Play。那是玩家的自由，但想让使用的命令还是游戏侧调整好让人安心使用比较好。  

- **让人注意到上述这些事**  
即使好不容易调整了，没让人注意到意图就没意义。  
像 eraKanon 那样角色或命令数量有限的话，让人调查也是乐趣之一，但大规模化的变体尝试的模式也庞大。  
如果被认为“效果不大不过是作为 Flavor 做的就这样吧…"，连提问都不会来。  
关于有效功能状况有限的命令，写在剧透用文本中，或在游戏中让村民说，有什么使用方法的提示比较好吧。  

即使一边听玩家意见一边调整，附上想朝这个方向性等作品或补丁的附言，意见也容易出来，也是采纳意见时的指针。  
做了〇〇命令但想做成能像□□那样区别使用，或者不想变△△的强度但不想让人乱放等。  
新功能也是 Flavor 的情况也那样写好。特别是发生条件难的，可能会无意中变成游戏进行上的陷阱。

### 使用版本管理系统

版本管理，简单来说就是留下更新履历，以便日后调查。  

用 zip 等保存旧数据，或在评论和文本文件中写进度情况等，留下履历是常有的事。  

这个方法的难点是，以文件为单位不知道文件中哪里不同，如果细致保存文件数和容量会增加。  
为此解决了问题的、专用的版本管理系统在编程中常用。  

基本用法是，事前安装版本管理系统，将变体等所在的文件夹，设为版本管理系统使用的设定。称为创建仓库 (Repository)。  
之后正常用编辑器保存后，每隔一定间隔，大体每追加 1 个功能，将变更的文件作为更新履历登记。称为提交 (Commit)。  

日后可以调查“某月某日变更的文件是哪个？”、“这个文件变更的是哪天和哪天？”等。  
想到“这部分是为了什么变更来着？”时可以追溯履历调查，如果觉得“这个变更果然失败了”也可以还原。  

使用 WinMerge 的人应该习惯差分显示，版本管理系统保存的就是这个差分。仅保存有变更的地方，所以比用 zip 保存全版本效率高。  

版本管理用数据是作业用，游玩不需要，所以分发文件中常不包含，但也有面向开发者添付的情况，也有不小心同捆的情况。  
实际上应该有相当多的人使用版本管理系统管理自制的变体或总结等。Emuera 的开发也在使用。  

开发补丁时，制作中本家版本升级等会让人困扰，但那种情况也因为差分可知更新履历，自己追加的部分和本家追加的部分，统合作业会变轻松。  
即使是同一文件，改写之处大多完全不同，那种情况几乎自动修正结束。  
也不易发生因用旧文件覆盖导致的 bug 复活，即使发生了也容易把握原因和修正。  

像补丁统合那样的作业也有难的部分，但仅变更记录和确认的话比较简单，有兴趣的人请挑战一次。  
原本是只有程序员使用的，但仅是管理文件的更新履历，其实可用于各种用途。  
Office 数据、插画、小说等领域也在用。不小心以奇怪状态覆盖了，或者之前的更好…等故障在任何领域都会发生。  

Subversion (SVN)、Git、Mercurial 等有很多，微妙擅长领域不同，但将差分作为更新履历登记，以便日后处理的机制都一样。  
看入门网站或比较网站，有感觉的就用那个，特别没有的话利用者多的 SVN 或 Git 困扰时容易查到。  
eraRorona 添付了名为 Bazaar 的系统的数据。  
哪个系统都好，但直接从命令行操作很辛苦，所以推荐使用 TortoiseSVN、TortoiseGit 或 SourceTree 等可用 GUI 操作的软件。
