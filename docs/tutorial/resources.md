# リソース設定 — 画像リソースの準備方法

!!! info "前提知識"

    - **前提章**: [HTMLタグ構文](html-syntax.md)（`<img>`タグの`src`属性でリソース名を参照）
    - **Reference分類**: [画像処理関連](../Reference/README.md#image)

    このページではEmueraで画像リソースを準備・使用する方法を解説します。各節の末尾にバリアントタグを付け、その機能をサポートする派生版を示します。

    | タグ | 派生版 |
    |------|--------|
    | *(なし)* | Emuera原版でサポート |
    | **EM+EE** | EM+EEで追加 |
    | **Skia** | Skia版で追加 |

---

## 概要

Emueraで画像を表示するには2つの要素が必要です：

1. **画像ファイル**（PNG/JPG/BMP/WebP/GIF）を`resources`フォルダに配置
2. **リソース定義ファイル**（CSV）でリソース名と画像の対応を宣言

リソース名は`<img src='リソース名'>`の`src`属性や`SPRITECREATED("リソース名")`などの式中関数で使用されます。

---

## リソース定義ファイル（CSV）

`resources`フォルダにCSV形式のテキストを配置すると、リソース定義ファイルとして読み込まれます。サブフォルダにも配置可能です（1.823以降）。

### スプライト定義

```csv
;コメント行
リソース名, ファイル名, x, y, width, height, posx, posy, delay, destWidth, destHeight
```

| パラメータ | 位置 | 必須 | 説明 |
|-----------|------|------|------|
| リソース名 | 1 | ✅ | `<img src='リソース名'>`や`SPRITECREATED("リソース名")`で使用。重複不可 |
| ファイル名 | 2 | ✅ | 画像ファイル名（拡張子含む）。CSVファイルからの相対パス。上位ディレクトリは不可 |
| x, y, width, height | 3–6 | | 元画像の切り出し領域（ピクセル）。省略時は画像全体を使用 |
| posx, posy | 7–8 | | 画像の相対位置オフセット。`SPRITEPOS`/`SPRITEMOVE`で動的変更可能。省略時は`0,0` |
| delay | 9 | | アニメーションフレームのみ有効。そのフレームの表示時間（ミリ秒）。省略時は`1000ms` |
| destWidth, destHeight | 10–11 | | 出力サイズ（ピクセル）。省略時は切り出し領域のサイズ |

!!! tag-variant "Skia"

    `destWidth`/`destHeight`パラメータはSkia版ではSQLiteメタデータインデックスに格納され、レンダリング時にオンデマンドでデコードされます。

### アニメーションスプライト定義

```csv
リソース名, ANIME, width, height
リソース名, ファイル名, x, y, width, height, posx, posy, delay, destWidth, destHeight
リソース名, ファイル名, x, y, width, height, posx, posy, delay, destWidth, destHeight
……
```

先頭行に`ANIME`を記述し、スプライト全体のサイズを指定（`width, height`は正の整数必須、省略不可）。以降の行で各フレームを定義します。

アニメーションスプライトは`INPUT`等の待機中、標準では再描画されません。`SETANIMETIMER`を実行して待機中の再描画を有効にしてください。

## 対応画像フォーマット

| フォーマット | Emuera | EM+EE | Skia | 説明 |
|-------------|--------|-------|------|------|
| BMP | ✅ | ✅ | ✅ | 無圧縮、ファイルサイズ大 |
| JPG | ✅ | ✅ | ✅ | 非可逆圧縮、透明非対応 |
| PNG | ✅ | ✅ | ✅ | 可逆圧縮、透明対応 |
| WebP | — | ✅ | ✅ | 高圧縮率、透明・アニメーション対応 |
| GIF（アニメーション） | — | — | ✅ | 多フレームアニメーション対応 |

ERB内から`GCREATEFROMFILE`や`SPRITECREATEFROMFILE`で動的に画像を読み込むことも可能です。

## Skia版のリソース管理機構 { #skia-resource-management }

!!! tag-variant "Skia"

    Skia版は画像リソース管理を全面的に再設計し、核心的な変更は「起動時全量ロード」から「オンデマンド読み込み + 階層型キャッシュ」への移行です。

### 遅延読み込みインデックス

CSVの事前読み込み時はSQLiteメモリインデックス（リソース名→ファイルパス+切り出し領域+出力サイズ）のみ構築し、画像データは0バイト。初回レンダリング時に`SKBitmap`へデコードされます。

CSVで定義されたリソース数に関わらず、起動時のメモリ消費はインデックスサイズのみに依存します。

### SharedBitmapCache — グローバルビットマッププール

グローバルLRUビットマッププール。最大容量200枚の`SKBitmap`、**ファイルパス**をキーとします。

- 同一ファイルは1回のみデコードされ、複数スプライトでビットマップを共有
- `ConstImage`はファイルパスのみを記録し、`SKBitmap`への参照を保持しない
- レンダリング時に`SharedBitmapCache.Get(filepath)`でオンデマンドデコード
- 容量超過時、最も古い未使用ビットマップが淘汰（Dispose）され、次回アクセス時に再デコード

### AnimSpriteCache — アニメーションスプライトキャッシュ

LRUキャッシュ。最大容量6個のアニメーションスプライト、**ファイルパス**をキーとします。

- 多フレームGIF/WebPアニメーション（`SpriteAnimated`）のみ管理。CSV ANIMEのフレーム結合アニメーションは対象外
- 容量超過時はEvictで全フレームデータを解放し、再アクセス時に再デコード
- Sprite Sheetモードでの同一ファイル重複デコードによるメモリ爆発を解決

### 2種類のアニメーションスプライトのキャッシュ差異

| 特性 | CSV ANIME（SpriteAnime） | GIF/WebPアニメーション（SpriteAnimated） |
|------|--------------------------|----------------------------------------|
| フレーム来源 | 複数の独立ファイルまたは同一ファイルの異なる領域 | 単一の多フレームファイル |
| キャッシュ機構 | 各フレームがSharedBitmapCache経由（max 200） | 全体がAnimSpriteCache経由（max 6） |
| メモリ使用量 | フレームファイル数に比例 | アニメーション数に比例（フレームデータは全体管理） |
| 淘汰動作 | 単一フレームビットマップがLRUで淘汰 | 全体がEvict/Reload |

## Skia版のリソース使用ガイドライン

!!! tag-variant "Skia"

### 実行時動的読み込みよりCSV登録を優先

Skia版の遅延読み込みインデックスにより、CSV登録リソースは起動時にメモリオーバーヘッドゼロ、初回レンダリング時にオンデマンドデコードされます。そのため**画像リソースはCSVに登録し、システムに一元管理させることを推奨**します。`SPRITECREATEFROMFILE`や`GCREATEFROMFILE`によるスクリプト層の手動読み込み・解放は推奨されません。

実行時動的読み込みの適用シナリオ：

| シナリオ | 推奨方式 | 理由 |
|---------|---------|------|
| 汎用画像リソース | CSV登録 | システムがライフサイクルを一元管理、手動Dispose不要 |
| 1回のみ使用する一時スプライト | `SPRITECREATEFROMFILE` | 使用後すぐ解放、CSVインデックスを浪費しない |
| GDRAW系で描画するアート文字・図形 | `GCREATEFROMFILE` | GraphicsImageは独立キャンバス、SharedBitmapCacheを経由しない |

!!! warning "SPRITECREATEFROMFILEの注意点"

    `SPRITECREATEFROMFILE`で作成したスプライトは`activeSprites`に登録されますが、CSVメタデータインデックスはありません。使用後に`SPRITEDISPOSE`で解放しないと、スプライトがメモリを占有し続けます。対照的に、CSV登録スプライトはシステムが`RELOAD`時や終了時に一括解放します。

### アニメーションスプライト：多フレームファイル形式を優先

CSV ANIME（SpriteAnime）の各フレームが異なる画像ファイルの場合、各フレームがSharedBitmapCacheのスロットを1つ占有します。アニメーションフレーム数が200を超えると、LRU淘汰によりデコード/解放サイクルが頻発し、メモリ使用量の急増とパフォーマンス低下を引き起こします。

**推奨されるアプローチ**：

| 方式 | 説明 | キャッシュ占有 |
|------|------|--------------|
| 多フレームGIF/WebP | 1ファイルに全フレームを含む | AnimSpriteCache 1スロット |
| スプライトシート | 全フレームを1枚の画像に結合、CSVで切り出し領域を指定 | SharedBitmapCache 1スロット |
| CSV ANIME + 複数ファイル | 各フレームが独立ファイル | SharedBitmapCache Nスロット（200フレーム超は非推奨） |

!!! example "スプライトシートの例"

    8フレームのアニメーションを8×1のフィルム画像`walk.png`に結合（各フレーム64×64、全体512×64）：

    ```csv
    WALK, ANIME, 64, 64
    WALK, walk.png, 0, 0, 64, 64, 0, 0, 100
    WALK, walk.png, 64, 0, 64, 64, 0, 0, 100
    WALK, walk.png, 128, 0, 64, 64, 0, 0, 100
    WALK, walk.png, 192, 0, 64, 64, 0, 0, 100
    WALK, walk.png, 256, 0, 64, 64, 0, 0, 100
    WALK, walk.png, 320, 0, 64, 64, 0, 0, 100
    WALK, walk.png, 384, 0, 64, 64, 0, 0, 100
    WALK, walk.png, 448, 0, 64, 64, 0, 0, 100
    ```

    全フレームが同じファイル`walk.png`を共有するため、SharedBitmapCacheは1スロットのみ占有します。

## 原版との差異

原版Emueraは起動時にCSVで指定された全画像ファイルをメモリに展開し終了まで占有します。そのため原版では「画像を単一ファイルに合成する」ことがメモリ最適化として推奨されていました。

Skia版はオンデマンド読み込み + LRUキャッシュに変更され、メモリ使用量が大幅に削減されました。複数ファイルのシナリオでも`SharedBitmapCache`が自動的にデコードとキャッシュを管理するため、「単一ファイルへの合成」はメモリ最適化の必須手段ではなくなりました——ただし、スプライトシートはキャッシュ効率の観点（1スロット vs Nスロット）から引き続きアニメーションスプライトのベストプラクティスです。
